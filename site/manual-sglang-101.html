How to read this manual

The SGLang documentation tells you what each flag does, and this manual tells you which ones matter, why they exist, and what we measured when we changed them.

sglang serve --help lists 535 options at version 0.5.22. Its documentation describes each of them. That list answers the question "what does this flag do".

It does not answer the questions that cost money. Which three settings matter on your first day? Which defaults assume a machine you do not have? Which published benchmark describes your workload?

This manual answers those questions. Every feature in SGLang is a receipt for something that cost too much. The radix cache is the receipt for computing the same system prompt twice. The overlap scheduler is the receipt for a GPU that waits while Python plans the next batch. Prefill and decode disaggregation is the receipt for long prompts that stall every other user.

Each section tells one of those stories. It gives the cost, the obvious fix and why it fails, and what SGLang does. Then it says what to measure and when to change the default.

Who this manual is for

You have called a model through an API, and now you want to serve an open model yourself. You know what a token and a GPU are. You have not read the scheduler or the cache of a serving engine. You want to know which settings matter before you pay for them.

After the last part, you can:

  • Start SGLang, send a request, and read every line the scheduler logs about it.
  • Compute the KV cache cost of a model, size the pool on purpose, and explain why a server runs out of memory.
  • Write prompts that hit the prefix cache, and prove the hit rate with cached_tokens and /metrics.
  • Benchmark a server, find the concurrency knee, and report TTFT, TPOT, and throughput together.
  • Choose between tensor, data, and expert parallelism and prefill-decode disaggregation from measurements.
  • Judge a published SGLang benchmark: its version, its workload, and the mechanism that explains its result.

Seven lessons go deeper into the ideas this manual applies. The serving internals lesson builds paged attention and continuous batching. The goodput lesson defines the metrics. The speculative decoding lesson builds EAGLE-3, and the quantization lesson covers the formats. The serving selection lesson, the inference optimization lesson, and the prompt caching lesson complete the set. This manual stays with SGLang.

SGLang on One Page

1.1

What a serving engine owns

SGLang owns the time between a request and its tokens: it decides which prompt tokens to compute, which to reuse, and when each request runs.

You downloaded an open model, wrote a loop that calls generate, and put it behind an HTTP endpoint. One user gets answers fast. Ten users wait in a line, the GPU sits idle between requests, and every request recomputes the same system prompt. A serving engine exists to fix exactly that loop.

When you finish this section, you can name the two phases of every request and the four numbers a server is judged by. You can also say what SGLang controls and what it leaves to others.

Two phases with two different bottlenecks

Prefill: the forward pass over the whole prompt. It computes the keys and values of every prompt token in one batch of matrix multiplications, and it produces the first output token. Decode: the loop that produces each next token, one forward pass per token per request.

The two phases stress different parts of the GPU. Prefill has many tokens per pass, so it keeps the arithmetic units busy. Decode has one new token per request per pass. Each step reads all the weights and cached keys and values to do little arithmetic. Decode speed is set by memory bandwidth, and prefill speed is set by compute.

We measured the difference on one Mac with a 0.6B model. A 512-token prompt reached its first token in a median of 163 ms. After that, each new token took 4.38 ms on average.

That is about 0.32 ms per prompt token against 4.38 ms per output token, a factor of about 14. Every design choice in this manual follows from that gap. Prefill work can be shared and skipped. Decode work can only be batched, so that one read of the weights serves many requests.

The four numbers

A server has to answer four questions, and a report that answers one of them answers nothing.

  • Time to first token (TTFT): how long a user waits before the first word. Prefill and queueing set it.
  • Time per output token (TPOT): the average gap between tokens after the first. Inter-token latency (ITL) is the same gap measured one token at a time, so its tail shows stalls. Decode sets both.
  • Throughput: output tokens per second across all users. Batching sets it.
  • Goodput: requests per second that meet a TTFT target and a TPOT target at the same time. It is the number your users feel.

The first three trade against each other. A larger batch raises throughput and makes each user's tokens slower. A large prefill chunk finishes a long prompt sooner and stalls every decode in the batch while it runs. Section 5.1 shows the trade on a real sweep, where more users bought no extra throughput and five times the wait.

SGLang's benchmark tool prints TTFT, TPOT, ITL, and throughput. It does not print goodput at v0.5.22, so you compute it from the per-request records yourself. The inference metrics lesson builds that calculation.

What SGLang owns, and what it does not

SGLang is three processes and a cache around a model. The tokenizer manager turns text into token ids. The scheduler decides which requests run in each forward pass, keeps the KV cache, and finds prompt prefixes it already computed. The detokenizer turns token ids back into text and streams it out. Section 2.1 follows a request through all three.

Three things stay outside. The model decides what the answer says. In our capture, a 0.6B model asked to name a planet answered "Ardens", which is no planet. SGLang served that answer correctly and fast, and no serving engine can make a model right.

The operator decides how much memory SGLang gets and which machine a request goes to. SGLang provides a separate router, the model gateway, for that second job, and section 6.4 covers it.

Where SGLang wins and where it loses

Every engine posts a benchmark where it wins. We read the reports by people outside the SGLang team, and they agree on a shape that follows from the mechanisms above.

SGLang wins when prompts repeat. A field report ran SGLang 0.5.6 and an 8B model on two H100 GPUs field Rawlinson 2025-12. With one user, TTFT was 583 ms against 2,141 ms for vLLM 0.11. That is the radix cache from section 3.3 skipping a prefill it already did.

SGLang ties on unique prompts and dense models. A field report ran SGLang 0.5.9 and Llama 3.3 70B in FP8 on one H100 field Spheron 2026. At 50 users it found 1,920 output tokens per second against 1,850. Both engines now run the same kernel families, so a 4% gap is noise for most teams.

SGLang loses TTFT on long prompts with its defaults. A field report on one H100 with 16K-token prompts measured a mean TTFT of 10.8 s against 1.9 s at 60 users field Jarvislabs 2026-05. The same run gave SGLang the best TPOT, 63 to 81 ms against 97 to 120 ms. SGLang splits a long prompt into chunks so that decodes keep moving, and it pays for that in first-token time.

SGLang is the reference engine for large mixture-of-experts models. SemiAnalysis made it the default engine for DeepSeek models in InferenceMAX field SemiAnalysis 2025-10. The first audited MLPerf result with SGLang ran DeepSeek-R1 on 512 MI355X GPUs field Crusoe 2026-09. Part 6 explains the parallelism that makes that work.

Our position

Choose SGLang for the shape of your traffic, never for a headline number. Agents, chat with a fixed system prompt, and retrieval with a fixed preamble all share long prefixes. For that traffic, SGLang's cache pays you back on every request. If every prompt is unique and long, measure both engines on your own prompts before you commit.

Distrust any SGLang benchmark that does not name its version. The most repeated number on the web, "SGLang 29% faster than vLLM", comes from one offline test whose page lists SGLang v0.2.3 next to vLLM 0.11 field AIMultiple 2026-01. At least five other posts copy it under other names. Section 5.3 shows how to read a benchmark before you believe it.

What to do with this
  • Report TTFT, TPOT, throughput, and goodput together, at a stated concurrency.
  • Expect prefill to cost a fraction of a millisecond per token and decode several milliseconds.
  • Pick SGLang when your prompts share prefixes, and measure it when they do not.
  • Check the SGLang version before you trust a benchmark number.

One request, end to end

One POST /generate with a five-token prompt crossed three processes, reused two cached tokens, and returned twelve tokens in 950 ms.

The fastest way to understand a serving engine is to send it one small request and read everything it writes about it. Most people skip this. They start the server, see "ready", and point a load test at it. Then the first surprise in production is a log line they never read.

When you finish this section, you can start SGLang on a laptop and send one request through each API. You can explain every timing and token count in the response.

Starting the server

We ran SGLang 0.5.22 on Apple silicon through its MLX backend, with a 4-bit Qwen3-0.6B. This is the command every capture in this manual starts from.

sglang serve is the entry point that SGLang recommends at v0.5.22. The older python -m sglang.launch_server still works and prints a warning. --disable-cuda-graph is in the Apple silicon instructions and does nothing useful on a Mac, and the server says it is deprecated. --mem-fraction-static 0.4 is our choice, and section 3.2 shows the crash that made us set it.

Before the first request, the server sizes its memory and builds its cache. Read these four lines on every start.

KV pool: the memory that holds the keys and values of every token the server keeps. It has room for 181,574 tokens here, at 114,688 bytes each. Section 3.1 derives that number from the model's shape. max_running_requests: the most requests the scheduler runs at once. The server computed 4096 from the pool size. Nobody set it.

The last line is printed after the server sends itself a request. SGLang posts "The capital city of France is" to its own /generate endpoint, then calls /freeze_gc. That freezes the Python garbage collector in all three processes, so the objects created at startup are never scanned again. Keep that detail in mind. It returns in the field report at the end of this section.

The request

We sent the native API a five-token prompt and asked for twelve tokens at temperature zero.

Read it field by field. The request waited 0.24 ms in the queue, because nothing else was running. Two of its five prompt tokens were already in the cache. Our prompt "The capital of France is" shares its first two tokens with the warm-up prompt "The capital city of France is". The radix cache found them and skipped them. The text "Paris, and the capital of Germany is Berlin. The capital" stopped at 12 tokens because we asked for 12, and finish_reason says length.

The scheduler logged the same request from its side.

#new-token: 3 and #cached-token: 2 add up to the five prompt tokens. That pair is the most useful line SGLang prints. Section 3.4 uses nothing else to find a broken prompt.

The first-token time is not what you think

The first token took 889 ms. The whole request took 950 ms, so the eleven tokens after the first took about 61 ms. After the warm-up of the benchmark tool, a 512-token prompt reached its first token in a median of 163 ms on the same server. A prompt that is 100 times longer started five times faster.

The prompt length did not cause the 889 ms. The first request of a new shape pays one-time costs. On MLX, the first request that reuses a cached prefix also ran slow in section 3.4. We did not find the exact cause in the log. The lesson holds on any backend. The first request after a start measures the start, and you should throw it away.

The same question through the OpenAI API

Most clients speak the OpenAI chat API, and SGLang serves it on the same port. We asked the chat endpoint to name one planet in one word, with thinking turned off.

A seven-word question became 21 prompt tokens, because the chat template wraps the message in role markers. That template cost is real. Count it when you budget context. The model said "Ardens", which is no planet. SGLang did its job: it ran the model the operator chose and returned its answer in 4 tokens.

cached_tokens appears here only because we started the server with --enable-cache-report. Without that flag, the OpenAI response reports no cached tokens at all, even when the scheduler reused thousands. Turn it on. It costs nothing, and it is the only way a client can see the cache.

Our position

Read the startup log before you send traffic, and warm the server before you measure it. The startup lines tell you the pool size, the request limit, and the cache type the server chose for you. All three were computed, and section 3.2 shows a case where the computed value crashed the server.

A field report from LinkedIn shows why the request path deserves the same attention as the kernels field LinkedIn 2026-02. Their ranking service ran a 0.6B model on 300-token inputs at 100 queries per second. The bottlenecks they found were tokenization, ZMQ messages between the processes, Python garbage collection, the GIL, and the scheduler. A scoring path that skips decode cut P99 latency from 6,220 ms to 454 ms. Garbage collection paused the server for 100 to 300 ms every few seconds. Their fix was a warm-up followed by a frozen collector, merged as pull request 9241.

That is the freeze you saw at startup.

What to do with this
  • Read the KV pool, max_running_requests, and tree cache lines on every server start.
  • Send warm-up requests before you measure anything.
  • Start the server with --enable-cache-report so clients can see cached_tokens.
  • Check #new-token and #cached-token in the scheduler log for each request you debug.

2.1

sglang serve and the three processes

SGLang splits one server into a tokenizer process, a scheduler process, and a detokenizer process, because Python text work must never delay the loop that feeds the GPU.

You start a server, send one request, and it works. Then you put real traffic on it, and the GPU sits at 40 percent while users wait. Most people blame the kernels first. LinkedIn did the work to find out, and the slow parts were the tokenizer, the messages between processes, Python garbage collection, and the GIL field LinkedIn 2026-02.

When you finish this section, you can start SGLang with sglang serve and name the three processes it starts. You can also read the startup log for the numbers that decide everything later.

The cost: one Python thread cannot do everything

A language model server does two kinds of work. GPU work is the forward pass: one prefill or decode step every few milliseconds. CPU work is everything around it: parsing HTTP, applying the chat template, tokenizing, turning token ids back into text, and checking stop strings.

The obvious design puts all of it in one Python process. That design fails under load. Python runs one thread at a time under the GIL. A 3,000-token prompt that is being tokenized holds the interpreter that must launch the next GPU step. Every millisecond of text work becomes a millisecond of idle GPU.

LinkedIn measured this on H100 GPUs with small ranking models. Batch tokenization alone moved P99 latency from 4,583 ms to 464 ms at 500 queries per second field LinkedIn 2026-02. The model did not change. Only the CPU path around it changed.

What SGLang starts

TokenizerManager: the object in the main process that receives each request, applies the chat template, tokenizes the text, and waits for the answer. The HTTP server and the TokenizerManager share one process and one asyncio loop.

Scheduler: a separate process that owns the GPU. It decides which tokens run next, builds the batch, runs the forward pass, and samples. With tensor parallelism there is one scheduler process per GPU.

DetokenizerManager: a third process that turns output token ids into text, one small piece at a time, and sends the text back to the TokenizerManager.

The processes talk over ZMQ sockets. The TokenizerManager sends a TokenizedGenerateReqInput to the scheduler. The scheduler sends a BatchTokenIDOutput to the detokenizer. The detokenizer sends a BatchStrOutput back. At v0.5.22 the messages are pickled by default, because SGLANG_USE_PICKLE_IPC is true code.

With tensor parallelism, only rank 0 of the scheduler opens the ZMQ sockets. It broadcasts each request to the other ranks, so every GPU builds the same batch code. No rank decides on its own.

The command we ran

We started the server on an Apple silicon Mac with the MLX backend and a 4-bit Qwen3 0.6B model. sglang serve is the recommended command at v0.5.22. The older python -m sglang.launch_server still works and prints a warning that names sglang serve as the recommended entrypoint code.

Two flags are not defaults, and both are deliberate. --enable-cache-report puts the cached token count into every OpenAI-style response, so section 2.5 can show it. --mem-fraction-static 0.4 limits the KV pool, and section 3.2 explains the crash we had without it.

The scheduler loop and --schedule-policy

The scheduler answers one question every few milliseconds, which tokens the GPU computes next, and at v0.5.22 its default answer is first come, first served.

Eight users send prompts in the same second. One of them pasted a 4,000-token document, and the others typed a sentence each. Should the long prompt go first, or the short ones? Should the request that shares a system prompt with yesterday's traffic jump the queue? Somebody has to decide, on every step, and in SGLang that somebody is the scheduler loop.

When you finish this section, you can read the scheduler's Prefill batch and Decode batch log lines. You can name the policy that orders the waiting queue and decide whether to change it.

The cost of a bad order

A GPU step costs about the same whether it computes tokens for 1 request or for 8. So the scheduler wants big batches. A user who waits in the queue sees nothing at all. So the scheduler also wants short queues. Every policy is a trade between those two costs.

The obvious fix is a smart order, for example the request with the most cached prefix first. The SGLang paper proposed exactly that, longest prefix match, and proved it optimal for an offline batch paper. Online traffic is not an offline batch, and the smart order costs CPU time on every step.

One turn of the loop

Scheduler loop: the function that runs forever in the scheduler process. Each turn takes new requests, picks the next batch, runs it on the GPU, and processes the results.

One turn does four things in order code:

  1. Ingest. Drain new requests from the ZMQ socket and add them to the waiting queue.
  2. Pick. If the last batch was a prefill, merge it into the running decode batch. Then try to build a new prefill batch from the waiting queue. If one exists, run it. If not, run one decode step for every running request.
  3. Run. Build a ForwardBatch from the ScheduleBatch and run the model.
  4. Process. Append the sampled tokens, check stop conditions, free or cache the KV of finished requests, and send results to the detokenizer.

A request rides one prefill batch, possibly over several chunks, and then joins the long-lived decode batch until it stops. Prefill wins when the scheduler can admit something. That rule keeps time to first token low, and section 2.3 shows the budget check that decides "can admit".

The two log lines

The scheduler prints one line per prefill batch and one decode line every 40 decode steps, the default of --decode-log-interval code. These lines are the most useful text the server writes. Here are three consecutive lines from our benchmark at concurrency 8.

Read the fields:

  • #new-seq is how many requests this prefill admits. #new-token is how many prompt tokens it computes, and #cached-token is how many it reused from the radix cache.
  • token usage is the share of the KV pool in use. Our pool is large, so usage stays near zero here.
  • #running-req counts requests that are decoding. #queue-req counts requests that are waiting.
  • cuda graph: False is expected on a Mac. On CUDA, True means the decode step replayed a captured graph, and section 4.1 explains why that matters.

The policies

Schedule policy: the rule that orders the waiting queue before admission. Set it with --schedule-policy.

The default at v0.5.22 is fcfs code. The choices split into two groups.

GroupPoliciesWhat they use
Cache-awarelpm, dfs-weight, hrrn, shortest-prefill-firstthe radix tree: how much of each prompt is already cached

Many readers expect lpm, because the paper describes it. It was the default in v0.4.3 and became fcfs by v0.4.6. The research for this manual did not find the pull request that changed it.

Two rules in the code limit the cache-aware policies code:

  • When the waiting queue holds more than 128 requests, lpm and hrrn change to FCFS for that turn. The comment says why: "Turn off the expensive prefix matching and sorting when the #queue is large."
  • When the radix cache is off, every cache-aware policy becomes FCFS.

So lpm helps only in a narrow band. The queue must be long enough to reorder, short enough to stay under 128, and full of shared prefixes.

Our position

Keep fcfs. It is fair, it costs no prefix matching on the hot path, and the radix cache still gives you the cache hits. A shared prefix that arrived first is in the tree when the next request matches it, whatever the order.

Switch to lpm only when three things are true. Your traffic shares long prefixes. Your queue is often between a few and 128 requests deep. You measured the cache hit rate before and after with /metrics. Section 5.2 shows the cache_hit_rate series to compare.

If you need tiers of users, use --enable-priority-scheduling instead of a cache policy. A new request can then preempt running ones when its priority beats theirs by --priority-scheduling-preemption-threshold, 10 by default code.

  • Keep the fcfs default unless you measured a cache gain from lpm.
  • Expect lpm to change to FCFS above 128 waiting requests.
  • Check the log for the effective limit after you set a limit.

2.3

Admission and retraction

SGLang admits a request only when a forecast of its future tokens fits the KV pool, so a full server queues new users instead of breaking the running ones.

Your dashboard says the GPU has free memory, yet new requests wait 28 seconds for their first token. Nothing crashed, nothing was dropped, and the per-token speed is fine. Users still feel that the service is down. This is what admission control looks like when it does its job, and you need to know why it chose to make them wait.

When you finish this section, you can explain the token budget that decides admission and compute how many requests fit in a pool. You can also tell a healthy queue from a retraction problem in the log.

The cost: memory you will need later

A request needs KV cache for its prompt now, and for every token it generates later. The scheduler does not know how many tokens a request will generate. It knows only max_new_tokens, the upper limit.

There are two obvious fixes, and both fail. Reserve the full max_new_tokens for everyone, and most of the pool sits empty, because most requests stop early at an end-of-sequence token. Reserve nothing, and the pool fills during decode, and the server must throw away work.

The forecast

SGLang uses a forecast with a correction. Two rules decide admission code:

  • A new request must fit its uncached prompt tokens plus its remaining max_new_tokens, clipped to 4,096 by SGLANG_CLIP_MAX_NEW_TOKENS_ESTIMATION.
  • Each running request holds back its remaining max_new_tokens times the new token ratio.

New token ratio: the share of remaining output that the scheduler expects a running request to use. It starts at 0.7 times --schedule-conservativeness (1.0 by default). It falls linearly to 0.14 of its start value, which is 0.098 at defaults, over 600 decode steps code.

The ratio falls because most requests stop early. The scheduler grows bolder the longer things go well. A request with ignore_eos set cannot stop early, so its ratio is always 1.0.

What we measured with a small pool

We started a server with --max-total-tokens 4096, a pool far smaller than our Mac allows. Then we ran the benchmark at concurrency 16 with 256-token prompts and 512-token outputs.

The benchmark client sets ignore_eos to true by default, so every request generates exactly 512 tokens code. Each request therefore reserves 256 plus 512, which is 768 tokens. Five requests reserve 3,840 tokens, and a sixth would need 4,608. The scheduler admitted exactly five.

Watch token usage. It climbs from 0.28 to 0.91 as the five requests generate into the space that the forecast reserved for them. Eleven requests wait the whole time. When the five finish, the next five start, and the log repeats in waves.

The client saw the cost of this order:

Every request succeeded. Once a request started, each token took 24 ms. The median user still waited 27.9 seconds for the first token. The Concurrency value of 13.06 is the client's average number of open requests. Only five of them were on the GPU at any time.

Retraction: when the forecast is wrong

The forecast can be too bold, because the ratio decays to 0.098. Requests that run long then need more slots than the pool has. Before each decode step, the scheduler checks that every running request can get one more slot code.

Retraction: removing running requests from the decode batch to free their KV slots, and putting them back in the waiting queue. They prefill again later.

When the check fails, SGLang logs KV cache pool is full. Retract requests.. It retracts the requests with the fewest output tokens first, and among those the longest prompts first, because they lost the least work code. It resets the ratio to a new estimate: tokens decoded so far plus 20 per request, divided by the total max_new_tokens. At v0.5.22, if even the last request cannot fit, it aborts that request with "Out of memory even after retracting all other requests" instead of looping.

Our small-pool run had no retractions at all. The metrics endpoint confirms it.

The forecast had nothing to correct. With ignore_eos, the reservation was exact. Real traffic stops early, so the ratio decays and admission becomes bolder, and retraction becomes possible.

Incidents: when retraction is the problem

A server running DeepSeek-R1 on eight H20 GPUs logged KV cache pool is full. Retract requests. on every rank, again and again, and then stopped answering health checks issue #8463. A commenter traced it to retraction that could not free enough memory and repeated forever. The issue closed without a fix. The abort of the last request at v0.5.22 addresses that loop.

Another user saw decode throughput fall from about 429 to between 20 and 38 tokens per second after a retraction, and stay there issue #26248. That issue closed for inactivity with no recorded cause. The lesson stands: a retraction in the log is a performance alarm.

Our position

Queueing is the honest failure. A queue keeps every running request fast and makes the overload visible in #queue-req and in time to first token. Retraction hides overload as wasted prefill.

The SGLang tuning docs say an occasional retraction, about one per minute, is fine. Treat more than that as a configuration bug. Raise --schedule-conservativeness, for example to 1.3, so the forecast starts higher. Or lower --max-running-requests. Do not fix it with a larger --mem-fraction-static alone, because section 3.2 shows what that costs.

Set realistic max_new_tokens in your clients. A client that asks for 4,096 tokens and uses 200 makes every new request look about 20 times bigger than it is.

What to do with this
  • Compute admission as uncached prompt plus max_new_tokens, against the free pool.
  • Read a long queue with fast tokens as admission control, not as a fault.
  • Alert when num_retracted_reqs grows faster than about one per minute.
  • Raise schedule-conservativeness before you add memory to stop retractions.
  • Send realistic max_new_tokens from clients so admission sizes requests correctly.

The overlap scheduler

The overlap scheduler prepares batch N+1 on the CPU while the GPU runs batch N, and at v0.5.22 it is the default path and the better-tested one.

Profile a simple serving loop and you find gaps on the GPU timeline between decode steps. In each gap the GPU waits while Python reads the sampled tokens, checks stop strings, frees memory, and builds the next batch. A decode step on a small model takes a few milliseconds, so a gap of one millisecond is a large share of the step.

When you finish this section, you can explain how SGLang hides the CPU work between steps and say when the overlap is off. You can decide whether --disable-overlap-schedule belongs in your command.

The cost: CPU time between GPU steps

Overlap scheduling: running the CPU work for one batch at the same time as the GPU work of another batch.

The SGLang team described the problem in the v0.4 release post. Batch scheduling, memory allocation, and prefix matching leave the GPU idle between steps team 2024-12. Their answer: "The scheduler runs one batch ahead and prepares all the metadata required for the next batch." They report a 1.1x throughput gain from it team 2024-12. That number is their claim, measured on their GPUs.

The obvious fix is a second thread that builds batches while the first one runs the GPU. Python threads share one interpreter, so a scheduler thread and a forward thread take turns. SGLang tried a thread first. Since pull request #11210 in October 2025 it uses two CUDA streams in one thread instead code.

How it works on CUDA

The loop launches batch N+1 on the GPU first, and then processes the results of batch N on the CPU code. The GPU never waits for the bookkeeping of the step before.

There is a problem. Batch N+1 needs the tokens that batch N sampled, and those tokens are still on the GPU when N+1 is built. SGLang builds N+1 with placeholder token ids. A FutureMap fills in the placeholders on the GPU from the output of N. The CPU never needs to read the tokens before the launch code.

How it works on a Mac

The MLX backend has its own overlap loop, event_loop_overlap_mlx code. MLX evaluates lazily, so the loop keeps two decode graphs queued with mx.async_eval. The docstring says the GPU executes the next step "back-to-back" with the current one. It adds: "there is no scheduling gap on the device." The chain breaks when a prefill arrives, a request finishes, or the waiting queue has new work. Then the loop builds a fresh step.

The scheduler is the same Python scheduler on CUDA and on MLX. The batching, the radix tree bookkeeping, and the log lines in section 2.2 are the same. Only the forward pass and the overlap mechanism differ.

What happened when we turned it off

The Apple silicon page of the SGLang docs lists --disable-overlap-schedule as one of the key parameters for the MLX backend. We added it to our server command and ran the concurrency 8 benchmark. The server answered its own warm-up and the benchmark warm-up. Then the scheduler died on the first batch of the real run.

Read the stack from the bottom. With the overlap off, the dispatcher picks event_loop_normal, the generic loop. That loop calls run_batch, which still relays the sampled tokens through the FutureMap of the overlap machinery. On MLX the buffer lives on the Metal device and the sampled tokens arrive on the CPU, and PyTorch refuses to mix them. The overlap loop for MLX does not take this path, so the default server never reaches it.

The main process then shut everything down. Every one of the 32 benchmark requests failed: 8 were cut off during their response, and 24 could not connect after the server was gone.

Our capture kit runs this configuration on every recording, and it fails the same way every time. We report it as we found it: a flag that the platform docs recommend crashes the platform at the pinned release.

A GPU incident with the same root

On CUDA, a user ran with overlap on and hit an allocation failure right after KV cache pool is full at 94 percent token usage issue #14972. Under overlap, the next batch is planned while the tokens of the previous one are still being computed. Retraction had to reason about requests that would finish one step later. A fix proposed in pull request #15626 closed without merge. At v0.5.22 the scheduler removes requests that will finish by length from the next decode batch. It also skips retraction in a step where finishing requests will free KV code.

Both stories have one lesson. Overlap is a second copy of the timeline in the scheduler's head, and every feature has to agree with it.

Our position

Leave the overlap on. It is the default, and it hides CPU time that you would otherwise pay on every step. At v0.5.22 it is also the path that the developers and most users run.

Turn it off for one reason: to rule it out while you debug a wrong output or a hang. Expect the off path to be less tested, and test it on your hardware before you depend on it. SGLang itself turns the overlap off where it cannot work, for example on Apple MPS without MLX and for speculative decoding on CPU code.

What to do with this
  • Keep the overlap scheduler on in production.
  • Use --disable-overlap-schedule only to isolate a bug, and test it first.
  • Do not add --disable-overlap-schedule on MLX at v0.5.22.
  • Read a scheduler traceback from the bottom to find the failing component.

Streaming, stop strings, and the OpenAI API

SGLang checks stop conditions in the scheduler and builds text in the detokenizer, and its native /generate endpoint reports the timing and cache data that the OpenAI format leaves out.

You stream a reply to a chat window, and the last word before your stop string arrives late. Or the stop string itself leaks into the text when speculative decoding is on. Or the client shows no cached_tokens at all, so you cannot tell whether your prompt hit the cache. All three are decisions about where text is made and who reports what.

When you finish this section, you can choose between the native /generate endpoint and the OpenAI endpoints. You can read every timing field in a native response and explain why streamed text sometimes waits.

Two APIs on one server

Native API: SGLang's own endpoints, mainly POST /generate. It takes text or token ids and sampling_params, and it returns a meta_info object with SGLang's own data.

OpenAI API: the /v1/chat/completions, /v1/completions, and /v1/models endpoints, in the format that OpenAI clients expect. The server applies the chat template before it tokenizes.

Both endpoints build the same internal request and cross the same three processes from section 2.1. The difference is what comes back.

What the native response tells you

Our capture kit sends one native request with 12 output tokens at temperature 0.

Every field answers a question you will ask in production:

  • finish_reason says why it stopped: length here, because the request asked for 12 tokens and got 12.
  • queue_time is 0.24 ms, so the request did not wait. Under load this number is the first one to grow.
  • first_token_latency is 889 ms and e2e_latency is 950 ms. The first token cost most of the time on a cold server.
  • num_retractions is 0. Section 2.3 explains what a nonzero value costs.
  • cached_tokens is 2 of 5 prompt tokens, all on the device and none from host memory.

Two cached tokens on the first request of our kit is a small mystery with a clean answer. Before it accepts traffic, the server warms up with the prompt "The capital city of France is" code. Our prompt was "The capital of France is". The first two tokens matched the warm-up in the radix tree. The cache does not care which user sent a prefix.

What the OpenAI response tells you

We asked for one planet in one word. The 4-bit 0.6B model answered "Ardens", which is not a planet. Keep that in mind when you judge a serving engine with a tiny model. The engine did its job: it stopped at token 151645, the end-of-turn token, and reported matched_stop.

The cached_tokens field is there only because our server runs with --enable-cache-report. Without the flag, SGLang omits the cache details from OpenAI usage, even though it computes them for every request code. The native meta_info reports cached_tokens either way.

A note for Mac readers. On MLX at v0.5.22, decode is greedy unless you pass --mlx-enable-sampling, so temperature, grammar masks, and output logprobs have no effect there. The help text of sglang serve says so. Our kit uses temperature 0, so its outputs are the same either way. Section 4.6 covers sampling and logprobs on GPUs.

Where stop strings are checked

Stop condition: a rule that ends a request. It can be a stop token, a stop string, a regex, the max_new_tokens limit, an abort, or the end of a grammar.

SGLang checks stop conditions in the scheduler, after each step, in a fixed order code. A stop string is checked before the end-of-sequence token. The code comment gives the reason. Speculative decoding can accept more than one token in a step. A token-based check "would trim only the last token and leak the stop string." The detokenizer only trims the matched stop text from the output.

Why streamed text waits

Two rules can delay a chunk code:

  • Incomplete characters. The detokenizer decodes incrementally with two offsets per request. If the new text ends in an incomplete UTF-8 character, it waits for the next token before it sends anything.
  • A possible stop string. If the tail of the text could be the start of a stop string, the output streamer holds it back. If the next tokens complete the stop string, the text never appears. If they do not, the held text goes out with the next chunk.

With the default --stream-interval 1, SGLang streams after every step. A non-streaming request still sends progress inside the server every 50 tokens, SGLANG_FORCE_STREAM_INTERVAL, so the TokenizerManager can track it code.

An incident: the detokenizer that never moved

The incomplete-character rule has a cost when the tokens never complete a character issue #34740. The detokenizer waits while the text ends in the replacement character U+FFFD. Byte tokens that never complete a character never advance the offsets. Every step then decodes the whole tail again, and the work grows with the square of the length. The report found it with a test setting that fills id 100, which decodes to U+FFFD on DeepSeek-V4-Pro. The issue was open when we checked.

Our position

Use the native /generate endpoint when you debug, measure, or build your own client. Its meta_info tells you queue time, first token latency, cache hits, and retractions per request. The OpenAI format has no place for most of that.

Use the OpenAI endpoints for applications that already speak that format. Start every server with --enable-cache-report, so those clients can see cache hits too. It costs nothing, and part 3 shows how much the number is worth.

What to do with this
  • Debug and measure with /generate and read its meta_info fields.
  • Start servers with --enable-cache-report so OpenAI clients see cached_tokens.
  • Expect streamed text to wait when its tail could start a stop string.
  • Judge the engine and the model separately when a small model answers wrong.

The KV pool and bytes per token

SGLang stores every token of every running request in one pool of fixed-size slots, so a model's bytes per token decide how many users one GPU can serve.

You rent a GPU with 80 GB of memory for an 8-billion-parameter model. The weights take about 16 GB, so most people expect room for a large number of users. Then the server queues requests at a few dozen concurrent conversations, and the GPU still shows free compute. The weights did not fill the memory. The keys and values of every token did.

When you finish this section, you can compute the KV cost of a model from its config. You can find the same number in the startup log and explain why SGLang counts capacity in tokens.

Why the cache exists

KV cache: the stored keys and values of every earlier token, for every layer, kept so that decode does not compute them again. A decode step makes one new token. That token attends to the keys and values of all the tokens before it. Without the cache, each new token would repeat the whole prefill of the conversation.

So the cache grows with two things: the length of each conversation and the number of conversations that run at the same time. After the weights, it is the largest user of memory in a serving engine. Every scheduling decision in Part 2 is a decision about this memory.

The formula, and our first measured number

For a model with ordinary multi-head or grouped-query attention, one token costs this many bytes:

2 × layers × KV heads × head dim × bytes per value

The 2 counts the key and the value. Grouped-query attention: several query heads share one key and value head, which is why modern models have far fewer KV heads than attention heads. SGLang computes this number when it starts code. On our Mac, the MLX backend printed it in the first lines of the log.

We measured bytes_per_slot=114688 for Qwen3-0.6B. The second line gives every term: 28 layers, 8 KV heads, a head dimension of 128, and bfloat16, which is 2 bytes. So the cost is 2 × 28 × 8 × 128 × 2, which is 114,688 bytes, or 112 KiB per token. The formula and the log agree to the byte.

Multi-head latent attention (MLA): DeepSeek's attention, which stores one compressed latent per token instead of separate keys and values per head. MLA is small per token, but every tensor-parallel rank stores the full latent code. Add GPUs with tensor parallelism and you do not add tokens. Section 6.1 shows how data-parallel attention answers that problem.

Two tables, one pool

SGLang keeps the KV cache in a pool of fixed-size slots, one slot per token. Two tables sit in front of it, and they answer different questions code.

ReqToTokenPool: a table with one row per running request and one column per token position. Each cell holds the index of a slot in the KV pool. Row 0 is padding, so that padded batch entries write to a harmless place.

TokenToKVPoolAllocator: the free list of KV slots. It gives out slot indices when a request needs room and takes them back when the request ends. Slot 0 is reserved for the same padding reason. That is why our log shows a buffer of 181,575 slots for a pool of 181,574.

The physical pool holds the tensors. Attention kernels read the keys and values through the request's row in ReqToTokenPool. This design has one large effect. Two requests that share a prefix can point their rows at the same slots, so the shared tokens exist once in memory. Section 3.3 shows the radix tree that finds those shared slots.

The cache is the pool

SGLang has no separate setting for cache size. The SGLang paper states the design directly: "we let the cached tokens and the currently running requests share the same memory pool" paper. A cached prefix is KV that no running request locks right now. When a new request needs room, SGLang evicts prefixes that no request locks, from the same pool.

This is why the startup log reports one number, max_total_num_tokens, and not two. On our Mac with --mem-fraction-static 0.4, that number was 181,574 tokens. The model allows a context of 40,960 tokens. So the pool holds four full-length conversations, or about 180 conversations of 1,000 tokens each. Running requests and cached prefixes compete for those same slots.

Our position: count tokens, not gigabytes

Size a deployment from max_total_num_tokens, not from free memory. Multiply your typical context length by the concurrency you need, and compare the product with that number. If the product is larger, the scheduler retracts or queues requests, and section 2.3 shows what that costs.

The two levers that change the number are the memory fraction in section 3.2 and the KV data type. --kv-cache-dtype defaults to auto, which keeps the model data type unless the checkpoint asks for FP8 code. FP8 halves the bytes per token.

A field report shows the size of that lever. Cloudflare reported that FP8 KV raised the context held in memory for Kimi K2.6 from about 686,000 to about 1.37 million tokens field Cloudflare 2026-08. The same report measured a few percent less throughput per request at low concurrency. At concurrency 64, the BF16 configuration ran out of memory, and the FP8 configuration reached 2,192 tokens per second. You trade a little speed per token for twice the users. Read the Cloudflare post for their accuracy checks before you copy the change.

What to measure

  • Read bytes_per_slot or compute it, and check that the two agree.
  • Read max_total_num_tokens in the startup log, and divide it by your typical context length.
  • Watch token usage in the scheduler log. It is the fraction of the pool that running requests and cached prefixes hold.

The lesson on inference optimization builds a KV cache from scratch, if you want the mechanism below SGLang.

What to do with this
  • Compute bytes per token from layers, KV heads, head dimension, and data type.
  • Check the computed number against bytes_per_slot in the startup log.
  • Plan capacity in tokens with max_total_num_tokens, not in gigabytes.
  • Expect MLA KV on every tensor-parallel rank, so more ranks add no tokens.
  • Try FP8 KV before you buy more GPUs, and check accuracy on your data.

3.2

--mem-fraction-static and startup sizing

SGLang sizes the KV pool once at startup from a snapshot of free memory, so a machine that changes after startup can kill the whole server.

Our first SGLang server on the capture Mac ran for four minutes. Then a benchmark at 32 concurrent requests crashed it with a Metal out-of-memory error, and every process of the server exited. The KV pool at that moment was 95 percent empty. The memory had gone to the pool, and the next prefill had nowhere to run.

When you finish this section, you can read how SGLang divides memory at startup and predict when that division fails. You can also set --mem-fraction-static on purpose.

The crash we recorded

We started the server twice before the capture kit existed, with the same command and no --mem-fraction-static. The two startups sized the pool very differently.

Nothing changed in SGLang between the runs. Other programs on the Mac used less memory at the second start, so sys_available grew from 27.81 GB to 38.29 GB. The pool grew with it, from 24.25 GB to 33.39 GB. Both budgets are 87.2 percent of the free memory, because the automatic mem_fraction_static resolved to 0.872.

Read token usage: 0.05 first. Thirty-two requests held 16,095 tokens, which is 5 percent of a 312,581-token pool. The pool reserved 34 GB and used under 2 GB of it. The activations of the next forward pass needed memory outside the pool, and the operating system had none left. One failed command buffer took down the scheduler, and the server killed its whole process tree.

How SGLang decides the split

--mem-fraction-static: the share of memory that SGLang gives to the model weights plus the KV pool. Everything outside that share is for activations, CUDA graphs, and other programs. The flag defaults to None, and SGLang computes a value at startup code.

On a GPU, the automatic value comes from a reserve. SGLang starts with 512 MB and adds 1.5 MB for each token of the prefill chunk code. Then it adds more for tensor and pipeline parallelism and for CUDA graphs. On a GPU with more than 60 GB, the reserve is at least 10 GiB. The fraction is then the GPU memory minus the reserve, divided by the GPU memory. When SGLang cannot read the device capacity, it uses 0.95.

After the weights load, SGLang measures free memory again. The KV budget is the free memory minus the 1 - fraction share of the memory that was free before loading code. The pool holds that budget divided by the bytes per token from section 3.1. If the budget is not positive, startup stops and prints the smallest fraction that would work.

The MLX backend on Apple silicon uses a simpler rule code. It takes the smaller of two numbers. The first is the fraction of the Metal working set, minus memory already in use. The second is the fraction of system memory available right now. The second term is the snapshot that changed between our two runs.

One public tuning write-up describes the fraction the other way round, as weights plus buffers, with the KV cache in the remainder. The code says the opposite: the static share holds the weights and the KV pool.

The default assumes the machine belongs to SGLang

The automatic rule is reasonable on a dedicated GPU. Nothing else allocates memory there, and the reserve covers the activations of one prefill chunk and the CUDA graphs. The rule fails in three common cases.

  • A shared machine. A laptop, a workstation, or a node with other jobs. The snapshot at startup does not hold for the life of the server.
  • Unknown capacity. On a device where SGLang cannot read the memory size, the fraction becomes 0.95 and leaves 5 percent for activations. Issue #39675 reports exactly that failure on Apple MPS, an out-of-memory error on the first prefill issue #39675.
  • Extra memory the estimate does not know about. Issue #42510 shows draft-model copies that stay in memory while the target pool is sized, so the draft pool allocation fails issue #42510. Issue #6027 shows a 64K-token DeepSeek-V3 prompt that ran out of memory in attention, although the log reported room for 274,934 KV tokens issue #6027.

Our position: set the fraction yourself on any shared machine

On a machine that runs anything besides SGLang, pass --mem-fraction-static yourself. The capture kit uses 0.4 on the Mac. With that value, the same benchmark that crashed run 2 finished all 128 requests at concurrency 32.

The budget is now 19.39 GB, which is 0.4 of the 48.49 GB snapshot. The pool still holds 181,574 tokens, far more than 32 requests of 640 tokens need. A smaller pool cost nothing in this workload, because the workload never filled the pool.

On a dedicated GPU, trust the automatic value first. Raise the fraction in steps of 0.02 only when the scheduler log shows a full pool and retractions. Find the upper limit in staging with your longest prompts, then run production one or two steps below it. Lower it when long prompts fail in attention, as in issue #6027.

The fraction also changes comparisons. One independent benchmark ran SGLang with its automatic fraction and vLLM with its default of 0.9 of GPU memory field Rawlinson 2025-12. The two engines had KV pools of very different sizes. Read section 5.3 before you trust a comparison that does not state both values.

What to measure

  • The max_total_num_tokens line at startup. It is the result of the whole calculation.
  • token usage in decode lines. A value near 1.0 means the pool is full.
  • The free memory of the machine during the heaviest prefill, from the operating system.

One more caution for Apple silicon. The kv_cache_memory_usage_gb metric read 0.0 in our capture, because the MLX backend allocates its own pool outside the accounting that the metric reads. Use the MlxAttentionKVPool log line, which reported about 19,860 MB.

What to do with this
  • Pass --mem-fraction-static yourself on any machine that runs other programs.
  • Read kv_budget and max_total_num_tokens in the startup log after every change.
  • Raise the fraction in small steps only when the pool is full and requests retract.
  • Lower the fraction when long prompts fail with out-of-memory errors in attention.
  • Compare engines only when both report their KV pool sizes.

3.3

RadixCache

RadixCache indexes every cached token run in a tree, so a new request reuses the longest matching prefix and prefills only the tokens after it.

A chat product sends the same 2,000-token system prompt with every question. A server without prefix reuse computes those 2,000 tokens for every request, and every user waits for the same work again. On our Mac, that repeated work made a shared-prefix benchmark take 129.7 seconds. With the radix cache on, the same benchmark took 48.8 seconds.

The tree

RadixCache: a radix tree over token sequences, whose nodes hold the KV slot indices of the tokens on their edges. The design comes from the SGLang paper, which calls the mechanism RadixAttention paper. A radix tree stores runs of tokens on its edges, so one node can hold a whole system prompt.

TreeNode: one node of the tree. It holds its children, keyed by their first token, and the token run on its edge code. It also holds the KV slot indices for those tokens, a lock count, a last-access time, and a hit count.

Four operations do all the work.

  1. match_prefix walks from the root and follows the child whose first token matches. If the match ends inside an edge, it splits that node so the boundary is exact. Every node on the path gets a new access time.
  2. insert walks the same way and adds a leaf for the tokens that did not match. If another request already inserted the same tokens, SGLang frees the duplicate slots and points the request at the tree's copy.
  3. inc_lock_ref and dec_lock_ref count the running requests that use a node. A count above zero protects the whole path to the root.
  4. evict frees leaves that no request locks, oldest first, and moves up the branch as leaves disappear.

One rule surprises people. A match can cover at most the prompt length minus one code. The last prompt token always goes through prefill, because the model needs its logits to sample the first output token. Our cache experiment shows that rule: a 2,999-token prompt reported 2,998 cached tokens and 1 new token.

Which tree you get at v0.5.22

The class name in old blog posts and issues is RadixCache. At v0.5.22 the default is UnifiedRadixCache, one tree that also handles sliding-window and Mamba state code. The tree walks run in a Rust core by default since v0.5.21. The log on our Mac shows the exception.

The no-cache server printed the same three lines. --disable-radix-cache still builds UnifiedRadixCache, in a disabled mode that matches nothing and inserts nothing. The separate ChunkCache class that older posts describe was deleted on 2026-10-08 issue #43201.

How the scheduler uses the tree

The default --schedule-policy is fcfs, first come, first served code. The paper's longest-prefix-match order, lpm, is a choice you make. The code sorts by prefix length only while 128 or fewer requests wait, because matching every waiting request costs time code. Above that, lpm uses the FCFS order.

The scheduler also avoids a waste inside one round. When several waiting requests share a prefix that is not cached yet, it lets one of them prefill the shared part first. The others reuse it in the next round. Section 2.2 covers the policies in full.

Our position: leave the radix cache on

The cache costs almost nothing when prompts do not repeat. Cached tokens live in the same pool as running requests, and eviction frees them on demand. We know of one reason to turn it off: to test whether a wrong answer comes from reused KV. Even then, try --kv-canary log first, which checks KV slots for corruption while the cache stays on code.

Then measure the hit rate together with every other feature you add. Issue #32459 is the warning issue #32459. A team that replayed multi-turn agent traffic saw a deep-prompt hit rate of 97 percent without speculative decoding, and 40 to 53 percent with EAGLE. Input throughput fell from 43,981 to 12,881 tokens per second, with no error in the logs. The candidate cause was the extra KV that speculative decoding reserves, which forced the tree to evict cached prompts.

Field reports put the folklore in proportion. vLLM also reuses prefixes, so engine comparisons measure two caches against each other. One independent test of 16 models on an A10G found SGLang ahead on repeated prefixes field Varad More 2026-04. The gain was 20 to 40 ms of first-token time at 7B to 9B. A RunPod test of a 70B model with a cached 7,000-token context measured 35.0 against 32.8 tokens per second per stream field RunPod 2025-06. The SGLang paper reports up to 6.4 times higher throughput paper, which is the authors' best case against the systems of 2024.

What to do with this
  • Leave the radix cache on, and turn it off only to isolate a KV bug.
  • Read #cached-token and #new-token in prefill lines to prove a hit.
  • Expect the last prompt token to prefill, even on a full hit.
  • Choose lpm only for offline batches with shared prefixes and short queues.
  • Measure the hit rate again after you add speculative decoding.

3.4

Prefix-friendly prompts

The prefix cache matches tokens from the first one, so one changing token near the start of a prompt costs more than any server setting can save.

A team runs DeepSeek-V4 for long agent sessions on eight GPUs, with hierarchical caching turned on. Their dashboards show #cached-token: 0 on requests that repeat 100,000 tokens of history. They tune the cache tiers and the write policy. The hit rate barely moves. Then they find a random hash that their relay put into the system prompt of every request.

When you finish this section, you can predict which prompts hit the prefix cache before you send them. You can also prove the hit rate with cached_tokens, the scheduler log, and /metrics.

The experiment: one identifier, three places

The capture kit sends one 2,999-token system prompt and one short question, five times in each of three forms. The server runs with --enable-cache-report, so each response reports its cached tokens to the client. The kit sends two warm-up requests first.

  • Stable: the same system prompt every time.
  • ID at start: the system prompt starts with Request id <random hex>., a new value on every request.
  • ID at end: the same random ID goes at the end of the system prompt.

We measured a 28 times longer wait for the first token when the ID sits at the start: 1,255 ms against 45 ms. The same ID at the end cost 43 ms more than the stable prompt. The tokens are almost the same in all three cases. Only their order differs.

The cached-token counts explain the times. The stable prompt reused 2,998 of 2,999 tokens, the maximum from section 3.3. The ID at the start matched only the first 5 tokens, the ones that come before the random hex digits. Every token after a change is a different branch of the tree, even when the rest of the prompt is identical.

Why the order matters

The radix tree compares tokens from the first one onward, and it stops at the first difference. Nothing after a difference can match, because the attention values of every later token depend on every earlier token. A cache that reused the later tokens would return wrong answers. So prefix caching is exact by design, and it is unforgiving by the same design.

The same rule applies to each part of a chat request. The chat template turns the messages into one token sequence in a fixed order: system prompt, tool list, earlier turns, new message. A change in the system prompt invalidates everything. A change in the newest message invalidates only that message.

The incident

Issue #35129 is the story at the top of this section issue #35129. The reporter found three causes stacked on top of each other.

  1. The relay put a per-session random cch= hash and a rotating system message into each request. Removing them moved the engine hit rate from 66.8 percent to 94.4 percent.
  2. The client wrote its task-list snapshot at the end of the system prompt. Every task update changed the system prompt, so it invalidated more than 100,000 tokens of history after it.
  3. Hierarchical cache load-back, when it could not find room, evicted the prefixes of other sessions. The reporter counted 250,000 evict calls against 376 completed load-backs.

The first fix was a prompt edit. No server flag in section 3.5 could have recovered the 27.6 points that the hash cost.

Our position: fix prompts before you tune the server

Treat the prompt layout as part of the serving system. Before you change any cache flag, check these rules against your real requests.

  • Put content that never changes first: the system prompt, then the tool list in a fixed order.
  • Put content that changes per session after that, and content that changes per request last.
  • Never put timestamps, request IDs, session hashes, or random sampling seeds in the system prompt. Send them as request metadata, or at the end.
  • Keep tool and function definitions in a stable order. A JSON object whose keys change order is a different token sequence.
  • Append to the conversation. Do not rewrite earlier turns, for example to summarize them, unless you accept a full prefill.

Two server-side settings break reuse in ways that look like prompt problems. A request for prompt log probabilities from position k can reuse only the first k tokens code. Different LoRA adapters never share tree nodes, even for identical tokens, because the adapter is part of the tree key code.

Routing can break reuse too. With several servers, a request that goes to a server without its prefix misses the cache, whatever the prompt looks like. Jarvislabs reported that routing each conversation to the same server moved their hit rate from 64.7 percent to 92.1 percent field Jarvislabs 2026-08. Section 6.4 shows how the gateway routes by prefix.

How to prove a hit

Use three measurements, from the closest to the request to the most general.

  1. In the response. Start the server with --enable-cache-report, which defaults to off code. The usage block then reports cached_tokens. The native /generate API returns cached_tokens in meta_info without the flag.
  2. In the scheduler log. Every Prefill batch line reports #new-token and #cached-token.
  3. In the metrics. /metrics exports sglang:cache_hit_rate, a gauge of recent prefill batches. After the shared-prefix benchmark in section 3.3, our server reported 0.94. The server with --disable-radix-cache reported 0.0.

The lessons on prompt caching and on caching and cost show the same rule for hosted model APIs. Those APIs bill cached input tokens at a lower price.

What to do with this
  • Put fixed content first and per-request content last in every prompt.
  • Keep IDs, timestamps, and hashes out of the system prompt.
  • Keep tool definitions and JSON keys in a fixed order.
  • Turn on --enable-cache-report and read cached_tokens in responses.
  • Check routing when the prompt is stable and the hit rate is still low.

3.5

Eviction policies and HiCache

When the GPU pool is full, SGLang evicts the least recently used prefix by default, and HiCache keeps evicted prefixes in host memory and in optional storage.

A coding agent holds a session of eight turns, and its history grows past 25,000 tokens. The GPU pool holds a few dozen such sessions. The ninety-first user arrives, and SGLang must evict a cached prefix to make room. When the first user returns, their history is gone, and the server computes all 25,000 tokens again.

When you finish this section, you can choose an eviction policy from a measured hit rate. You can also decide when hierarchical caching pays for its cost and which of its settings to change first.

What eviction removes

Eviction removes only cached tokens that no running request locks, the leaves of the radix tree. It never removes the KV of a running request. That case is retraction, and section 2.3 covers it. Eviction starts from the leaves with the lowest score and moves toward the root.

--radix-eviction-policy decides the score code. The default is lru.

PolicyEvicts firstWhen it helps
lruthe prefix with the oldest last accessmost workloads, the default
lfuthe prefix with the fewest hits, then the oldesta hot set of prompts that stays stable for hours
slruprefixes with fewer than 2 hits, then the oldesta stable hot set with a stream of one-time prompts

tlruhistory that cannot change the next turn's prefill timemulti-turn agents with a tail-latency target

Tail-Optimized LRU (tlru): a policy that keeps only the part of a conversation that the next turn's latency target needs, and evicts the rest first. It comes from a paper that the code names, arXiv 2510.15152. The SGLang team reports 43.9 percent lower p99 inter-token latency on DeepSeek-V4-Pro at concurrency 32 team 2026-10. That number comes from the release notes of v0.5.21, and we found no independent test of it.

Our position: keep lru until you have measured a reason

The SGLang docs give the same advice: start with lru and change it only against a measured hit rate docs. Frequency-based policies hurt when popularity shifts, because yesterday's popular prompt stays in memory and today's prompt pays for it. Change the policy only when you can name the workload that the new policy serves, and measure the hit rate before and after.

HiCache: three tiers for one tree

HiCache: SGLang's hierarchical cache, which extends the radix tree from GPU memory to host memory and to a storage backend. --enable-hierarchical-cache turns it on, and it defaults to off code. The tiers have names in the code and the docs.

  • L1: the GPU pool from section 3.1.
  • L2: a pool in pinned host memory, private to one server instance.
  • L3: an optional storage backend shared across instances, set with --hicache-storage-backend. The choices include file, mooncake, hf3fs, and nixl.

The tree records where the KV of each node lives. A match returns a GPU hit and a host hit length. SGLang then loads the host part back into fresh GPU slots, one layer ahead of the computation that needs it docs.

--hicache-write-policy decides when a node gets a copy in host memory. The default is write_through. The code sets a hit threshold of 1 for write_through and 2 for write_through_selective code. So write_through copies a prefix on its first hit, and write_through_selective waits for a second hit. write_back copies a node only when the GPU evicts it.

The settings that decide whether it helps

L3 prefetch has its own rules. SGLang skips a storage prefetch when the storage hit is shorter than 256 tokens code. The default prefetch policy is timeout, which stops waiting for storage after a time that grows with the prompt.

The docs and the code disagree on that time. The docs give a base of 2 seconds, 0.1 seconds per 1,024 tokens, and a maximum of 30 seconds docs. The code at v0.5.22 uses a base of 1.0 second and 0.25 seconds per 1,024 tokens code. We found no maximum in the cache code. The code wins. A 100,000-token prompt can wait about 25 seconds for storage before SGLang computes it again.

The host pool size comes from --hicache-ratio or --hicache-size. Without either, SGLang takes up to --hicache-host-memory-fraction, which defaults to 0.8 of available host memory code.

What other teams measured

We could not run HiCache on the capture Mac, and the field evidence is thin. The numbers we found come from the SGLang team and its partners.

  • The SGLang RBG team and the Mooncake team ran a multi-turn benchmark on Kubernetes field Alibaba Cloud 2026-03. The average time to first token was 5.91 seconds with GPU memory only. The L2 tier lowered it to 3.77 seconds, and a Mooncake L3 lowered it to 2.58 seconds.
  • The SGLang HiCache post quotes Novita team 2025-09. Novita reported a 56 percent lower average time to first token, and a hit rate that rose from 40 to 80 percent.

The failure reports are better documented than the successes. In issue #35129, load-back that found no room evicted other sessions' GPU prefixes, with 250,000 evict calls against 376 completed load-backs issue #35129. Our position: add HiCache for long sessions, and add it in steps

HiCache pays for itself when sessions outlive the GPU pool: multi-turn chat, coding agents, and long documents asked several times. For short one-time prompts it adds copies and load-backs with nothing to reuse. Add it in this order, and measure the hit rate and the p99 time to first token at each step.

  1. Make prompts prefix-stable first, as in section 3.4.
  2. Turn on L2 only, with the default write_through.
  3. Switch to write_through_selective if host copies use too much PCIe bandwidth.
  4. Add an L3 backend when several instances should share prefixes.
  5. Change the eviction policy last.
What to do with this

  • Turn on HiCache for long multi-turn sessions, not for one-time prompts.
  • Start HiCache with host memory only, then add storage after you measure.
  • Trust the code's prefetch timeouts over the docs at v0.5.22.

Hybrid models and the cache

Sliding-window and Mamba layers keep state that a token-level tree cannot split at any position, so hybrid models are where SGLang's cache fails today.

A team serves a hybrid model that mixes linear-attention layers with full-attention layers. They turn on HiCache and run twenty requests that hit the host tier. All twenty answers are fluent and on topic for a different prompt. The usage block reports full cached tokens, and nothing in the logs warns them.

When you finish this section, you can say why hybrid models break the simple picture of the radix tree. You can also test the cache on your model before your users test it for you.

Three kinds of layer state

The radix tree in section 3.3 works because full attention stores one key and one value per token. A cached prefix of any length is valid, so the tree can split a node at any token. Two other kinds of layer break that rule.

Sliding-window attention (SWA): attention that reads only the last few thousand tokens. A SWA layer needs only the window, so SGLang keeps a smaller pool for SWA layers and drops KV that leaves the window. A cached prefix is useful only where the window's KV still exists.

Mamba layer: a state-space or linear-attention layer that keeps one fixed-size recurrent state per sequence, updated token by token. The state at token 2,000 summarizes all 2,000 tokens. It cannot be cut back to token 1,500. A prefix can resume only where SGLang saved a snapshot of the state.

Our capture model has neither. The startup log says so.

Read these two lines on your own model first. hybrid_swa=True or hybrid_ssm=True means that everything in this section applies to you.

How SGLang handles each kind

UnifiedRadixCache keeps one tree with a component for each kind of state code. Each node holds data for the full-attention component and, when needed, for the SWA and Mamba components. A match advances only while every component agrees that the state at that position is valid.

For SWA, the tree keeps a marker where window KV was dropped, and a match stops at the marker. --swa-full-tokens-ratio sets the size of the SWA pool against the full pool. It defaults to None, and model-specific overrides set it. The DeepSeek-V4 override sets it to 0.1 code.

For Mamba, the tree stores state snapshots on some nodes and copies a snapshot when a request reuses it. --mamba-radix-cache-strategy chooses how SGLang keeps snapshots: auto by default, no_buffer, extra_buffer, or extra_buffer_lazy code. --mamba-track-interval sets how often decode saves a snapshot, every 256 tokens by default.

What goes wrong, in the issues

Most open cache bugs at v0.5.22 involve hybrid models. These four show the range.

  1. A wrong answer from a host-tier hit. Issue #39830 is the opening story of this section issue #39830. A hybrid linear-attention model with HiCache gave fluent answers to a different prompt on 20 of 20 host-tier hits. Cold requests and GPU hits were correct. Earlier reports of the same class exist on the GPU path.
  2. Zero reuse for an identical prompt. In issue #22935, the match of a repeated prompt ends inside an edge, and the node split creates a node with no Mamba state issue #22935. The match stops at the last node with state, so the identical prompt reuses nothing.
  3. A strategy that makes the first token 4.7 times slower. In issue #37834, an option forced the no_buffer strategy issue #37834. The snapshot sat at a depth that later requests could not reach. On a retrieval workload the hit rate fell from 88.2 to 65.9 percent. The mean time to first token rose from 226 ms to 1,063 ms.
  4. A default that slowed decode. Issue #36131 reports a new default that frees SWA slots outside the window issue #36131. It reduced single-stream decode throughput for hybrid SWA models on DGX Spark and Thor.

Our position: test the cache on a hybrid model before you trust it

On a full-attention model, a wrong cache hit is rare enough that we leave the cache on and move on. On a hybrid model, run three checks before production. Each one takes minutes.

  1. Correctness. Send the same prompts cold, with a GPU hit, and, if you use HiCache, with a host-tier hit. Compare the outputs at temperature 0. Run --kv-canary log during the test, which checks KV slots for corruption and keeps the server running code.
  2. Reuse. Repeat a prompt and read #cached-token. An identical prompt that shows a small count has hit the split problem of issue #22935.
  3. Latency. Measure the time to first token with --mamba-radix-cache-strategy auto and with the strategy your deployment guide recommends. Keep the faster one only if the hit rate holds.

Then read the open issues for your model family before each upgrade. Between 2026-09-01 and the v0.5.22 tag, 334 commits touched the cache code. On hybrid models, a new release can fix one of these bugs and add another.

  • Read hybrid_swa and hybrid_ssm in the startup log for every new model.
  • Compare cold, GPU-hit, and host-hit outputs at temperature 0 before production.
  • Run --kv-canary log during cache tests on hybrid models.
  • Check that an identical prompt shows a high cached-token count.
  • Read the open cache issues for your model family before each upgrade.

4.1

ForwardMode and CUDA graphs

A decode step is too small to keep a GPU busy, so SGLang records its kernel launches once as a CUDA graph and replays the record on every step.

You serve a small model to one user on an H100 and watch tokens arrive. The GPU is fast, yet a profiler shows gaps between kernels. A field report from Hazy Research field Hazy Research 2025-09 measured that SGLang and vLLM used about half of the H100 memory bandwidth for Llama-1B at batch 1. The GPU waits for the CPU to tell it what to do next.

When you finish this section, you can name the mode of any forward pass and explain what a CUDA graph saves. You can also read the batch sizes SGLang captures and keep busy decode inside a graph.

Every forward pass has a mode

ForwardMode: the label on a batch that tells the model runner what kind of pass to run. The scheduler sets it, and the model runner, the attention backend, and the graph runners all read it.

ModeWhat the pass does
EXTENDPrefill. It writes KV entries for many new tokens. Part of the prompt can already be in the cache.
DECODEOne new token for each running request.
MIXEDA chunk of prefill and the decode tokens in one batch. Off unless you pass --enable-mixed-chunk.
IDLENo tokens. A data-parallel attention rank with no work runs it so that collective calls still match.
TARGET_VERIFYSpeculative decoding: the target model scores the draft tokens.
DRAFT_EXTEND_V2Speculative decoding: the draft model reads the accepted tokens.
PREBUILTA decode worker in prefill-decode disaggregation. The KV cache arrived from another server.
SPLIT_PREFILLA prefill that runs a few layers at a time, for prefill-decode multiplexing.

SGLang calls any pass that writes many KV entries per request "extend". That is why TARGET_VERIFY counts as extend in the code. The target model runs over several draft positions per request, like a small prefill with a tree mask.

The cost: one decode step is a long list of small launches

A transformer layer is a sequence of kernels: a norm, the QKV projection, attention, the output projection, a second norm, and the MLP. A 28-layer model launches hundreds of kernels to produce one token. During prefill each kernel works on thousands of tokens, so launch time is small next to compute time. During decode each kernel works on one token per request.

At batch 1 the GPU often finishes a kernel before the Python process has sent the next one. The obvious fix is a faster launch path, such as fewer Python calls. That helps a little, but each kernel still needs its own CPU launch, and the count does not change.

CUDA graph: a record of kernel launches with fixed tensor shapes and addresses, which the GPU can replay with one CPU call.

The record has a price. Every captured shape uses GPU memory, and a batch must match a captured shape exactly. SGLang pays that price for decode and pads each batch up to the next captured size.

What SGLang captures, and when it gives up

Capture bucket: one batch size that SGLang records a decode graph for at startup. Without speculative decoding, v0.5.22 captures sizes 1, 2, 4, 8, and 12, then every eighth size from 16 to 256. Above 256 it captures every sixteenth size to 511, then every thirty-second size up to the largest. A batch of 13 requests replays the graph for 16 and wastes three slots.

The largest bucket, max_bs, depends on GPU memory and tensor parallel size. The startup code picks it when you do not set --cuda-graph-max-bs-decode.

The cliff in field reports

A field report from Jarvislabs field Jarvislabs 2026-05 ran Qwen2.5-7B on one H100 with default SGLang flags. At concurrency 300, mean inter-token latency was 17.72 ms against 12.28 ms for vLLM. With no concurrency cap it was 100.92 ms against 28.84 ms. The post does not record the SGLang version or the server logs.

Our reading is a hypothesis, labeled as one. The default decode max_bs on that GPU is 256, and the latency break sits just above it. The maintainers saw the same shape on smaller cards. The code comment on the 20 to 35 GB tier says the old cap "forced eager decode at bs>=32 and collapsed high-concurrency throughput vs vLLM" code. PR #37898 raised that cap from 24 to 48 on 2026-09-04.

Our position

Keep CUDA graphs on, and size them to your traffic. The default max_bs suits moderate concurrency. If your benchmark or your production peak runs more requests than that, set --cuda-graph-max-bs-decode and --max-running-requests to your target before you measure. SemiAnalysis InferenceX recipes field InferenceX 2026-05 derive both values from the concurrency they test.

Do not turn graphs off to fix memory. If capture runs out of memory, lower --cuda-graph-max-bs-decode or --mem-fraction-static. A server without decode graphs pays launch time on every token for every user.

The flag --cuda-graph-max-bs no longer exists. We passed it to the v0.5.22 argument parser and it exited with ambiguous option: --cuda-graph-max-bs could match --cuda-graph-max-bs-decode, --cuda-graph-max-bs-prefill.

--attention-backend

SGLang has many attention kernels because none wins on every GPU and model, and its default choice records regressions that someone already paid for.

In January 2026 a user upgraded FlashInfer and served Qwen3-235B on H20 GPUs. Median inter-token latency went from 39.44 ms to 283.52 ms, seven times slower, and nothing else in the setup had changed. The FA3 kernel gave 56.73 ms on the same run. That report is issue #17411, and the code that picks your attention backend at v0.5.22 still cites it.

When you finish this section, you can name the backend SGLang picks for your GPU and model, and explain why. You can also split prefill and decode across two backends and decide when to override the default.

What an attention backend is

Attention backend: the class that computes attention over the paged KV cache for one batch. Every backend implements the same interface. It builds per-batch metadata such as page tables and index buffers. It prepares state for CUDA graph capture and replay. It runs forward_extend for prefill and forward_decode for decode.

The model code never calls a kernel by name. Each attention layer calls whatever backend the model runner installed at startup. So one flag swaps the kernel for every layer of every model.

At v0.5.22 the flag accepts 25 names. Two are aliases (nsa for dsa, and compressed for dsv4), so there are 23 backends.

The obvious fix, and why it fails

The obvious fix is to read a benchmark, find the fastest kernel, and pass it on every server. That fails because each backend has limits that a benchmark does not show.

trtllm_mha rejects speculative decoding with topk above 1 and does not run on SM120. FlashInfer cannot run models that use attention sinks. fa4 has a native page size of 128. Some backends accept FP8 KV caches and some do not. A kernel that wins on one model and GPU can refuse to start on the next.

How SGLang picks a default

When you do not pass --attention-backend, startup calls one function that reads your GPU, the attention type of the model, and your speculative decoding settings.

For MHA models, such as Llama and Qwen, the order is this:

  1. On Hopper with CUDA 12.3 or later, and no speculative topk above 1, the default is fa3. The code comment cites issue #17411.
  2. On Blackwell SM100 or SM103, the default is trtllm_mha, or fa4 when K and V widths differ.
  3. On AMD the default is aiter, and on Apple MPS it is torch_native.
  4. In every other case the default is flashinfer when it is installed and the model has no attention sinks, else triton.

For MLA models, such as DeepSeek V3, Hopper gets fa3 and Blackwell gets flashinfer. AMD gets aiter when each rank has 16 or 128 KV heads. A model override then moves DeepSeek V3 on SM100 to trtllm_mla.

The docstring of the same function says FA3 is avoided when the page size is above 1. The code does not check the page size. When a comment and the code disagree, the code is what runs.

Two backends in one server

Prefill and decode stress different things. Prefill reads long query blocks, and decode reads one query against a long cache. --prefill-attention-backend and --decode-attention-backend set each phase separately. When they differ, SGLang wraps both in a hybrid backend that dispatches by ForwardMode. With speculative decoding, --speculative-attention-mode decides which of the two runs the verify pass. Its default is prefill.

Docs and code disagree

The attention backend page in the docs at v0.5.22 still lists Cutlass MLA and Dual Chunk FlashAttention. PR #32114 deleted both on 2026-09-10, and neither name is a valid choice at the tag. The same page says Blackwell MHA uses trtllm_mha. The code picks fa4 for models with asymmetric K and V widths. In both cases the code wins, and this manual follows the code.

What to measure

Read the resolved backend in the startup log before you benchmark anything. Then change one flag, rerun the same benchmark at your real concurrency, and compare inter-token latency at p50 and p99. Attention is one part of a decode step, so a faster kernel can move end-to-end numbers less than its own benchmark suggests.

On our Mac capture, SGLang ran through the MLX runtime. MLX has its own attention path, so none of these backends ran there.

Our position

Leave --attention-backend unset unless you have a benchmark on your own traffic. The default encodes regressions that other users found, such as #17411, and model overrides, such as DeepSeek V3 on SM100. The same issue is also the exception: a user who measures can beat a default that a library upgrade broke. Measure, then override, and write the reason next to the flag.

Prefer the backend that supports every feature you need over the one that wins a microbenchmark. Speculative decoding with topk above 1 needs flashinfer, fa3, or triton when the page size is above 1.

  • Read the resolved attention backend in the startup log before every benchmark.

  • Check feature limits, such as speculative topk and page size, before choosing a backend.

4.3

--quantization and --kv-cache-dtype

Quantization buys memory first and speed second, and SGLang keeps weights, GEMM kernels, and the KV cache as three separate choices so that you can buy only what you need.

Cloudflare served Kimi K2.6 with a BF16 KV cache and raised concurrency step by step. At 32 concurrent requests the server produced 1,558 tok/s. At 64 it ran out of memory. With an FP8 KV cache the same service reached 2,192 tok/s at 64 requests, about 41% above the best BF16 result field Cloudflare 2026-08. The FP8 cache was slower per token at every concurrency both versions could run. It won because twice as many requests fit.

When you finish this section, you can tell weight quantization from KV cache quantization, and load a quantized checkpoint without breaking detection. You can also size the memory gain before you measure speed, and decide where a lower precision belongs.

Three choices, three flags

Weight quantization: storing the model weights in fewer bits, such as FP8, FP4, or INT4. It shrinks the weights and the memory traffic of each GEMM. --quantization selects the method.

GEMM backend: the kernel library that multiplies quantized weights. --fp8-gemm-backend and --fp4-gemm-backend select it, and both default to auto, which picks by GPU generation.

KV cache dtype: the format of the cached keys and values. --kv-cache-dtype selects it, separately from the weights. Its default auto uses the model dtype.

A model can run FP8 weights with a BF16 KV cache, or BF16 weights with an FP8 KV cache. Each choice moves a different budget, so treat them as three decisions.

Weights: offline first

At v0.5.22, --quantization accepts 31 method names. Most of them describe a checkpoint that someone already quantized: AWQ, GPTQ, ModelOpt FP8 and FP4, compressed-tensors, GGUF, Quark, and others. A few quantize BF16 weights while the model loads: fp8, mxfp8, nvfp4_online, and mlx_q4 or mlx_q8 on Apple silicon.

Offline quantization: the checkpoint already stores low-bit weights and their scales. Online quantization: SGLang converts full-precision weights at load time.

When you load a quantized checkpoint, do not pass --quantization. The model config check reads quantization_config.quant_method from the checkpoint and uses it. If you pass a method that differs, the check accepts only known compatible pairs, such as modelopt_fp4 on a modelopt checkpoint. For a requantization it logs that you should validate accuracy again. Every other mismatch raises at startup.

The flag can also block an upgrade. A GPTQ checkpoint loaded with no flag is detected, converted at runtime, and served by the Marlin kernel. The upgrade code accepts that conversion only when you passed no method or gptq_marlin.

PR #32114 deleted the plain GPTQ CUDA kernel on 2026-09-10, and on a CUDA build the method registry has no gptq entry. The flag parser still accepts --quantization gptq. The model config check then skips the Marlin upgrade and raises Unknown quantization method: gptq. We read this path in the code and did not run it on a GPU.

The KV cache: capacity, with a scale

--kv-cache-dtype accepts auto, bf16, fp8_e4m3, fp8_e5m2, mxfp8 (FA4 only), nvfp4, and fp4_mx_block16. FP8 halves the bytes per token and FP4 quarters them, so the same pool holds two or four times as many tokens. Section 3.1 shows how to compute bytes per token for your model.

FP8 needs a scale for each tensor. The help text of --quantization-param-path says the file "should generally be supplied, when KV cache dtype is FP8" and that without it the scales "default to 1.0, which may cause accuracy issues" code. Run an accuracy check whenever you change the KV cache dtype.

Cloudflare published its check. On Kimi K2.6, BF16 against FP8 KV scored 94.24 and 94.09 on GSM8K, 89.11 and 89.04 on MMLU, and 80.29 and 79.29 on MMLU-Pro field Cloudflare 2026-08. Those are their numbers on their model, and your model can differ.

Quantization is a capacity decision

Cloudflare also tested INT4 weights on GLM 5.2 field Cloudflare 2026-08. Decode got faster, 60 to 92 tok/s at concurrency 1 and 1,672 to 1,933 tok/s at 64. Prefill got slower, from about 10,160 tok/s with FP8 to about 8,660 with INT4.

Decode is limited by memory traffic, so smaller weights help. Prefill is limited by compute, and dequantizing INT4 costs compute. Cloudflare split the two phases across servers and runs INT4 for decode and FP8 for prefill. Section 6.3 explains the split.

Our position

Use an offline-quantized checkpoint and pass no --quantization flag. The docs say the same: "offline quantization is recommended over online quantization" docs. Online quantization adds load time and gives you a checkpoint that nobody evaluated.

Choose a KV cache dtype from memory, not from speed. If your server queues requests because the pool is full, an FP8 cache with a scale file is the cheapest capacity you can buy. If the pool has room, keep the model dtype.

Quantize per phase when you run prefill and decode on separate servers. Smaller weights help decode, and they can slow prefill.

4.4

--speculative-algorithm

Speculative decoding spends idle GPU compute to commit several tokens per step, so it cuts latency at low load and costs throughput when the GPU is already full.

A user turned on EAGLE-3 for Llama-3.1-8B on an A6000 and ran two tests. At batch 1, output went from 42.0 to 92.5 tok/s, more than twice as fast. At concurrency 20, output fell from 217.8 to 164.4 tok/s, a quarter slower. Both numbers are in issue #5274, and both are correct. A maintainer answered that speculative decoding "is for small batch sizes rather than stress tests" issue #5274.

When you finish this section, you can explain draft, verify, and acceptance length, and read the defaults SGLang picks. You can also find the request limit that speculation sets and decide where speculation belongs.

The cost: decode is one token at a time

Each decode step commits one token per request, and the next step needs that token as input. At batch 1 a step reads every weight of the model to compute one token. The GPU has compute to spare and memory traffic is the limit. A larger batch fills that spare compute with other requests.

Speculative decoding fills it with guesses. Draft model: a small model, or a small head trained on the target model, that proposes the next few tokens cheaply. Verify pass: one forward of the target model over all proposed tokens at once. The target accepts the longest prefix that matches what it would have produced, and adds one token of its own.

Acceptance length: the number of tokens committed per verify pass, accepted drafts plus that one bonus token. An acceptance length of 3 means one target forward commits three tokens.

One step in SGLang

  1. Draft. The draft model runs --speculative-num-steps times. With --speculative-eagle-topk above 1, each step keeps several candidates per node and grows a tree. A tree builder keeps the best --speculative-num-draft-tokens nodes and builds a tree mask.
  2. Verify. The target runs once in TARGET_VERIFY mode over every draft token with the tree mask. For greedy requests it keeps the longest matching path. For sampled requests it compares probabilities with temperature, top-k, and top-p applied.
  3. Draft extend. The draft model reads the accepted tokens in DRAFT_EXTEND_V2 mode, so its cache is ready for the next step.

The accept thresholds --speculative-accept-threshold-single and --speculative-accept-threshold-acc default to 1.0. With those values, a greedy request produces the same tokens it would produce without speculation.

The algorithms and the defaults

--speculative-algorithm accepts EAGLE, EAGLE3, NEXTN, STANDALONE, NGRAM, DFLASH, DSPARK, and UNO. NEXTN is another name for EAGLE. For DeepSeek V3 and other models that include multi-token prediction layers in the checkpoint, SGLang sets the draft model path to the model path. NGRAM needs no draft model at all. It looks up repeated token sequences in the text it has already seen.

When you leave the shape unset, SGLang chooses (num_steps, topk, num_draft_tokens) from the model architecture.

ModelDefault shape
LlamaForCausalLM, Grok(5, 4, 8): a tree of up to 8 drafts
DeepSeek, GLM, GPT-OSS, MiMo, STANDALONE, and every other model(3, 1, 4): a chain of 3 drafts

With topk 1, the code forces the draft token count to the step count plus one.

The limit nobody asked for

The EAGLE, NGRAM, DFLASH, and DSPARK handlers at v0.5.22 each do the same thing when you did not set --max-running-requests. It sets the value to 48 and logs one warning: "Max running requests is reset to 48 for speculative decoding" code. Speculation needs memory for draft tokens and works best at small batch, so the cap protects the server. It also caps your benchmark.

A throughput test with speculation on and no explicit limit measures a server that admits 48 requests. If your traffic runs 200 concurrent requests, the other 152 wait in the queue, and time to first token grows. The warning prints once at startup, and it scrolls away before the first request.

What to measure

The scheduler logs accept len and accept rate on each decode log line, and /metrics exports sglang:spec_accept_length and sglang:spec_accept_rate. Measure them on your own prompts, because acceptance depends on the text and on the draft. A field report by David Noel Ng field David Noel Ng 2026-08 on two GH200 measured 3.5 to 5.05 tokens on DeepSeek-V4-Flash after a loader fix.

Our position

Treat speculative decoding as a latency tool for low and middle concurrency. Turn it on for interactive traffic with a few users per replica. Leave it off for batch jobs and for servers that run at high concurrency.

Always set --max-running-requests yourself when speculation is on. Choose it from the concurrency where your sweep shows speculation still wins.

Use the draft layers that come with your model first. A model with multi-token prediction layers needs no extra download. For EAGLE-3, check that the draft model supports your prompt length, and train a draft on your own traffic when acceptance is low. Google Cloud team Google Cloud 2025-11 and Modal with Decagon team Modal 2025-11 both trained their own drafts. Modal reported 38% longer acceptance than open-source drafts. Both are vendor reports.

--grammar-backend and structured outputs

SGLang turns a JSON schema or regex into a token mask for every decode step, and compiles each grammar outside the batch loop.

Your agent asks the model for a tool call and parses the reply with json.loads. Most replies parse. A few have a missing brace, a trailing comment, or a field the schema does not allow, and the agent retries. Each retry costs a full generation and a full round trip, and the slow tail of your latency is now made of retries.

When you finish this section, you can constrain output with a JSON schema, a regex, or an EBNF grammar. You can also explain what the mask costs, read the grammar queue, and decide what to check after generation.

The obvious fix, and why it fails

The obvious fix is to validate after generation and retry on failure. That works and stays slow. It also fails in the cases you care about most. A model that broke the schema once on a prompt tends to break it again on that prompt.

Constrained decoding: removing every token that would break the grammar before the sampler picks one. The output then satisfies every rule that the backend enforces, so those rules become a property of the server.

What SGLang does

A request carries one constraint in its sampling parameters: json_schema, regex, ebnf, or structural_tag. The OpenAI chat API maps response_format to the same fields. --grammar-backend picks the engine that compiles it. The default at v0.5.22 is xgrammar, and outlines, llguidance, and none are the other choices.

  1. Look up. The grammar manager builds a key from the constraint type and its text, such as ("json", schema). A compiled grammar for that key comes back from the cache at once.
  2. Compile. On a miss, compilation starts in a thread pool and returns a future. The request moves to the grammar queue instead of the waiting queue.
  3. Admit. Each scheduler loop polls the futures. With tensor or data parallelism, a request is admitted only when its grammar is ready on every rank. It fails if compilation failed on any rank. An invalid grammar is cached as invalid, so the next request with the same schema fails at once.
  4. Mask. At every step the grammar fills a vocabulary bitmask, and the model runner applies it to the logits before sampling. With the overlap scheduler, the mask for the next step is built while the GPU runs the current one.
  5. Advance. After sampling, the grammar accepts the chosen token. With speculative decoding, it rolls back the rejected draft tokens.

On Apple silicon, the MLX runtime applies grammar masks only with --mlx-enable-sampling. Without that flag every decode step takes the highest logit, as section 4.6 shows from the help text.

Grammar queue: the list of requests whose grammar is still compiling. /metrics exports its length as sglang:num_grammar_queue_reqs.

Jump-forward is not active at v0.5.22

The SGLang paper describes jump-forward decoding. When the grammar allows only one continuation, such as the fixed text {"name": ", the server writes it without running the model. The grammar classes at v0.5.22 still have the jump-forward methods. A search of the runtime finds no caller outside the grammar classes. The scheduler does not use them, so expect one forward per token even inside fixed text. We read this in the code and did not run a timing test.

What to measure

Measure three things on your own schemas. First, the time to first token for the first request with a new schema against the second request with the same schema. The difference is compile time. Second, inter-token latency with and without the constraint at your real concurrency. The mask costs CPU time on every step. Third, the grammar queue length under load.

A field report by Varad More field Varad More 2026-04 measured structured generation on one A10G across 16 models from 2B to 9B. On 14 of the 16, vLLM was faster. The report does not separate compile time from per-token cost, so read it as a reason to measure, not as a verdict.

Our position

Constrain every response that a program parses. A mask is cheaper than a retry.

Do not trust the grammar backend to enforce every JSON Schema keyword. Test each keyword your consumer depends on, such as minLength, pattern, minimum, and enum, with a request that tries to break it. Keep a cheap validator behind the server for the fields that matter.

Send a few requests with each common schema after every deploy, so the first user request does not pay the compile time.

Incidents

The same report says outlines dropped pattern and numeric bounds. The issue was open when this manual was verified.

Grammar work grew with output length under speculation. Issue #38863 (2026-09-10): with speculative decoding, the host CPU time to build bitmasks grew with the length of the output. The cause was a rollback method that copied a debug list on every call. The issue was open as a performance report.

What to do with this
  • Use json_schema or response_format for every response that a program parses.
  • Test each JSON Schema keyword you rely on with a request designed to break it.
  • Send each common schema once after deploy so users do not pay compile time.
  • Watch sglang:num_grammar_queue_reqs when you add new schemas under load.

4.6

--enable-deterministic-inference and logprobs

The same prompt can give different tokens when the batch around it changes, and SGLang fixes the reduction order for each model and backend it has tested.

You run an evaluation twice at temperature 0 and the scores differ. You send one prompt alone and then inside a busy batch, and the second answer diverges after forty tokens. Nothing in your request changed. The server changed the batch your request ran in, and the batch changed the arithmetic.

When you finish this section, you can explain why batching changes output and what deterministic mode switches. You can also read the logprobs SGLang returns and test whether your model is deterministic.

The cost: addition order depends on the batch

Floating-point addition is not associative. Summing the same numbers in a different order can change the last bits of the result. A matrix multiply, a softmax, or a norm splits its sums into tiles, and many kernels pick the tile split from the batch size. A request in a batch of 1 and the same request in a batch of 37 go through different splits.

A difference in the last bit can change which token has the highest logit. After one different token, every later token is conditioned on a different text. Thinking Machines described this effect in a 2025 post on nondeterminism in inference field Thinking Machines 2025-09, and SGLang built its deterministic mode on the same approach.

Batch invariance: a kernel property. The result for one row does not depend on the other rows in the batch, because the reduction order is fixed.

What the flag switches

--enable-deterministic-inference is off by default. --rl-on-policy-target fsdp turns it on too. When it is on, startup does the following:

  1. It replaces the PyTorch operators aten::mm, addmm, _log_softmax, mean.dim, rms_norm, and bmm with batch-invariant kernels.
  2. It forces the pytorch sampling backend.
  3. With tensor parallelism on CUDA, it sets NCCL_ALGO=allreduce:tree, so the all-reduce sums in a fixed order. On AMD it uses a one-stage all-reduce.
  4. It accepts only the attention backends ascend, fa3, fa4, flashinfer, intel_xpu, and triton.
  5. It turns the radix cache off unless the attention backend is ascend, fa3, fa4, or triton.
  6. It gives every request without a sampling_seed the seed 42.

The fifth point matters most for a server. With flashinfer, deterministic mode turns off prefix caching. Every repeated prefix pays its full prefill again. Section 3.3 explains what that cache saves.

Logprobs are temperature-scaled

Logprob: the log probability of a token under the distribution the server sampled from. SGLang returns it when a request sets return_logprob or the OpenAI logprobs field.

The sampler computes returned logprobs as log_softmax(logits / temperature) when the batch is not all greedy. It returns log_softmax(logits) without the temperature only for all-greedy batches or when the environment variable SGLANG_RETURN_ORIGINAL_LOGPROB is set. A request at temperature 0.7 gets logprobs of the sharpened distribution.

That is correct for sampling, and it surprises anyone who compares those numbers with a model run at temperature 1. A reinforcement learning trainer that computes logprobs from the raw logits sees a mismatch on every token, and the mismatch looks like a numerical bug. Section 7.2 shows why that matters for training.

On Apple silicon

Our capture ran on the MLX runtime, and MLX treats sampling differently. The help text for --mlx-enable-sampling says what changes.

Without that flag, every decode step on MLX takes the token with the highest logit, whatever temperature the request asks for. Grammar masks and output logprobs also need the flag, and penalties never apply on MLX. Our capture kit sends temperature 0, so its results do not depend on this flag.

What to measure

SGLang includes a test that sends one prompt in random batch sizes and counts distinct outputs. It has three modes: single, prefix for shared prefixes, and radix_cache for cached against uncached prefill.

python3 -m sglang.test.test_deterministic --n-trials 50 --test-mode single
python3 -m sglang.test.test_deterministic --n-start 1 --n-trials 50 --test-mode prefix

Run it against your model, your attention backend, and your parallel layout. One distinct output per prompt is the pass condition. Then measure throughput with the flag on and off, because batch-invariant kernels give up some speed.

Our position

Treat --enable-deterministic-inference as a promise for one model on one backend, and test that promise. Turn it on for reinforcement learning rollouts and for evaluations you want to reproduce. Leave it off for production traffic, where prefix caching and faster kernels are worth more than identical bits.

Set sampling_seed on each request that must reproduce. Seed 42 for everyone makes every sampled request draw the same random numbers.

Incidents

The flag was accepted and the output still varied. Issue #43055 (2026-10-08): gpt-oss-20b gave several different greedy outputs for one prompt in prefix mode. Comments traced it to the deterministic Triton extend kernel on sliding-window layers. It aligned KV tiles to the trimmed prefix and not to absolute positions. The issue was open when this manual was verified.

Some architectures are not covered yet. Issue #43413 reported that a Mamba2 hybrid model was not batch-invariant. Issues #36174 and #31261 list DeepSeek-V4 and Qwen3.5 as not yet supported in deterministic mode.

A restart changed greedy output. Issue #39597 (2026-09-15): with the DFLASH speculative algorithm, the same prompt gave different text after a restart. FlashInfer autotuning picked different kernel tactics on each start. The workaround was --disable-flashinfer-autotune or deterministic mode.

What to do with this
  • Run sglang.test.test_deterministic on your model and backend before you rely on reproducible output.
  • Expect deterministic mode to turn off prefix caching on flashinfer, and pick fa3 or triton.
  • Set SGLANG_RETURN_ORIGINAL_LOGPROB when a trainer compares logprobs at temperature 1.
  • Pass --mlx-enable-sampling on Apple silicon when requests need temperature or logprobs.

Read the report, block by block

The function calculate_metrics in the benchmark module computes every line. Five of them are easy to misread.

Concurrency: the sum of every request's end-to-end latency divided by the run duration. It is the average number of requests in progress, measured after the fact. Here it is 7.96 against a cap of 8. It tells you the cap was reached, and nothing more.

Peak concurrent requests: the run is cut into one-second buckets, and each request counts in every bucket that its interval touches. The line reports the largest bucket count. Two requests that run one after the other inside the same second both count, so the number can exceed the cap. That is why the report says 16 at a cap of 8, and 64 at a cap of 32.

TTFT: the time from sending the request to receiving the first streamed chunk. It contains queueing, prefill, and the network.

TPOT: for each request, the time after the first token divided by the remaining tokens, (latency - ttft) / (output_len - 1). The report gives the mean and percentiles over requests. ITL: every gap between two streamed chunks, pooled across all requests. A chunk with several tokens counts as one gap.

Max ITL: the single longest gap, here 1,948 ms. One request waited almost two seconds between two tokens while new prompts ran their prefill. The median ITL of 20 ms hides that stall. The P99 of 79 ms shows part of it.

Then enforce the knee outside the engine. The engine's own limit is set from memory, and memory runs out long after latency is unacceptable. Put the cap in your client, your gateway, or --max-running-requests, and size it from the sweep.

Both numbers came from one scrape of the server in our capture. One is a gauge that remembers the last prefill batch it logged. The other is a pair of counters that remember everything.

When you finish this section, you can turn the endpoint on and tell a gauge from a counter and a histogram. You can compute a hit rate that means something, and write six alerts for a server past its knee.

The endpoint is off by default. The field enable_metrics defaults to False at v0.5.22 code, and without --enable-metrics the path /metrics returns nothing useful. Our capture server started with the flag, as section 5.1 shows. After the default experiments, it exported 81 metric families in 603 sample lines that start with sglang:.

Three kinds of series

Gauge: a value the scheduler overwrites on each log interval, such as the number of running requests. A scrape sees the latest value only. Counter: a total that only grows, such as the number of prompt tokens processed. You read it with a rate over a window. Histogram: a set of counters, one per bucket, that counts how many requests fell under each limit. You read percentiles from it with a rate over a window.

Reading other people's SGLang benchmarks

A published SGLang result depends on its version, workload, memory budget, graph ceiling, and kernels, so you read those five before you read the number.

The most repeated SGLang number on the web is "29 percent faster than vLLM": 16,215 tokens per second against 12,553. It comes from one offline test by the analyst firm AIMultiple, updated 2026-01-25 field AIMultiple 2026-01. That page lists SGLang as "v0.2.3" next to vLLM 0.11.0, a gap of about two years of releases. At least five later posts repeat the pair, some under the names of other companies. None of them reran the test.

When you finish this section, you can take a published SGLang benchmark apart into its five inputs. You can decide whether it applies to you and name the mechanism behind it. You can also say where the independent tests agree, which is a shorter list than the headlines suggest.

The five inputs behind every result

A benchmark result is a function of five inputs. Most disagreements between published reports trace back to one of them.

  1. Workload shape. Input length, output length, concurrency, and the share of the prompt that repeats. The radix cache helps only when prefixes repeat. Long inputs stress prefill. High concurrency stresses the scheduler and the KV pool.
  2. Memory budget. SGLang computes --mem-fraction-static from the GPU when you leave it unset. vLLM uses --gpu-memory-utilization 0.9. A test that sets one and not the other compares two different KV pools.
  3. CUDA graph ceiling. The decode step replays a captured CUDA graph only up to a batch size limit. Above it, decode runs eager, one kernel launch at a time. Section 4.1 explains the mechanism.
  4. Kernel path. The attention backend, the MoE kernel, and the quantization format. Several reports below were decided by a kernel that did or did not exist for one GPU.
  5. Version and date. One analyst measured the same model on the same AMD GPU at 20.4 and then 2,256 tokens per second per GPU, 26 days apart.

The code sets the third input from GPU memory at startup. Take an 80 GB H100 with tensor parallel size below 4. The default decode graph limit is 256, and the chunked prefill size is 8,192. On a 32 GB card the limit is 48, raised from 24 on 2026-09-04. The code comment on that change says the old cap "collapsed high-concurrency throughput vs vLLM" code.

Six questions before you trust a number

  1. Is the SGLang version stated? Without it, the result describes an unknown build.
  2. Does the workload match yours? Unique prompts say nothing about a chat server with a long shared system prompt.
  3. Were the memory budgets matched across engines?
  4. Did the concurrency pass the decode graph limit? If yes, the test measured eager decode.
  5. Are the flags mapped correctly? The same idea has different flag names in each engine.
  6. Who paid for the test? A GPU cloud, a hardware vendor, a competitor, or the SGLang team each has a reason to like one answer.

6.1

--tp-size, --dp-size, and --attn-dp-size

Tensor parallelism makes a model fit, data parallelism adds capacity, and attention data parallelism removes the KV copies that tensor parallelism makes for MLA models.

You have eight GPUs and one large model. The first command most people type is --tp-size 8, and the model loads. Then a teammate asks why the server holds so few tokens of KV cache for a DeepSeek model on 640 GB of memory. The answer is in how SGLang splits one model across GPUs, and in a flag whose meaning changed in v0.5.22.

When you finish this section, you can choose --tp-size, --dp-size, and --attn-dp-size for a model and a GPU count. You can also say which GPUs share which work, and read an old recipe that uses --enable-dp-attention.

One world, many ways to split it

Model world: the set of GPUs that together hold one copy of the model. SGLang builds it from two numbers only. The code raises an error when the world size is not tp_size times pp_size code.

Tensor parallelism (TP): each layer's weight matrices are cut into --tp-size slices, one per GPU. Every layer then ends with a collective operation that joins the slices. Pipeline parallelism (PP): whole layers go to different GPUs in order, and --pp-size sets the number of stages.

Everything else splits that same world. Attention data parallelism, expert parallelism, and context parallelism do not add GPUs. They regroup the GPUs of the TP group differently for different layers.

Keep one mental model, and every later flag reads clearly. TP size is the number of GPUs in one model copy. The other widths are ways to cut that set.

The default of every one of these flags is 1 code. So a plain sglang serve uses one GPU, one scheduler, and one copy of the model.

Two meanings of "data parallel"

Data parallelism (DP): several complete copies of the model, each with its own requests and its own KV cache. --dp-size 2 with --tp-size 4 uses eight GPUs as two worlds of four. A data parallel controller process gives each new request to one of the copies code. Its default method, auto, resolves to round_robin outside prefill-decode disaggregation.

Attention data parallelism: inside one TP group, the attention layers run data parallel while the feed-forward or expert layers stay split across all GPUs. Each attention group has its own scheduler, its own requests, and its own KV cache. --attn-dp-size 4 with --tp-size 8 gives four attention groups of two GPUs each.

Before v0.5.22, one flag carried both meanings. --dp-size counted model copies, unless --enable-dp-attention was also set, when it counted attention groups. Pull request #41818 gave the reason for the change in one sentence: "--dp-size means two different things... Every reader has to look at both flags to know which meaning it has." It was merged on 2026-09-30.

The code at v0.5.22 does three things with the old spelling code:

You passSGLang does

The warning names the new flag, and a comment in the code says to remove the old flag after 2026-12-31 code. Most DeepSeek recipes on the web still use the old spelling. They work today and stop working in a later release.

Why attention gets its own data parallel mode

DeepSeek models use multi-head latent attention (MLA). MLA stores one compressed latent vector per token and layer, which is one KV "head". Section 3.1 works through its size. Tensor parallelism cannot split one head across GPUs, so with --tp-size 8 every GPU stores the full latent cache for every token. Eight GPUs then hold eight copies of the same KV cache.

The SGLang team gave this reason when they added the mode in v0.4 team 2024-12. With attention data parallelism, each attention group keeps only its own requests. The KV capacity of the server grows with the number of groups. The team reported up to 1.9 times more decode throughput for DeepSeek models, which is their claim.

For a dense model with grouped-query attention (GQA), the reason does not hold. GQA has several KV heads, so tensor parallelism already splits the cache without copies.

What attention data parallelism changes for you

Turning on attention data parallelism changes two other settings without a flag of their own code:

  • chunked_prefill_size is divided by --attn-dp-size. A chunk size that you tuned on one GPU becomes smaller per attention group. The server log prints the old and the new value.
  • schedule_conservativeness is multiplied by 0.3. The scheduler then admits new requests with a smaller reservation for future tokens. Section 2.3 explains that reservation.

The first change is the one that surprises people. A team that measured TTFT with --chunked-prefill-size 8192 and then added --attn-dp-size 8 now runs chunks of 1024 tokens. Long prompts take more scheduler steps to prefill.

Our position

Use tensor parallelism to make the model fit, and nothing more. Add capacity with data parallel copies, inside one server with --dp-size or as separate servers behind the gateway in section 6.4. Use --attn-dp-size equal to --tp-size for MLA mixture-of-experts models such as DeepSeek and Kimi, and leave it at 1 for dense GQA models.

A field report supports the order. A student team tuned DeepSeek-R1 for a competition on H100 and H200 nodes field Lowndes 2025-11. Plain --tp 16 gave about 5.9k tokens per second offline. Their best layout, TP4 with DP4, PP2, and attention data parallelism on one H200 node, gave 17,417 tokens per second. Use their numbers as one data point, because the write-up explains --mem-fraction-static incorrectly.

Ant Group made the same kind of choice in production. Their DeepSeek-R1 decode runs on two nodes with 16 attention groups and 16-way expert parallelism field Ant-Group 2025-09.

Several nodes

One model world can span machines. Three flags describe it code:

6.2

MoE serving: --moe-a2a-backend, DeepEP, and EPLB

A mixture-of-experts layer sends every token to the GPUs that hold its experts, so MoE serving is mostly communication, and the busiest GPU sets the pace.

A mixture-of-experts (MoE) model such as DeepSeek-V3 activates a few experts per token out of many. On paper that is cheap compute. In a server it is a traffic problem. Each token must travel to the GPUs that hold its chosen experts, and each result must travel back, in every MoE layer of every step. One overloaded GPU then makes all the others wait.

When you finish this section, you can follow one token through an MoE layer in SGLang. You can also choose an all-to-all backend and an expert parallel size, and decide when to turn on load balancing and batch overlap.

One MoE layer, five stages

Expert parallelism (EP): the experts of each MoE layer are divided among GPUs, and tokens move to the experts. --ep-size sets how many GPUs share the experts. Its default is 1 code.

SGLang cuts the MoE forward pass into stages with one owner each docs. The router picks experts for each token. The dispatcher moves tokens to the GPUs that hold those experts. A runner computes all local experts with grouped matrix multiplications. The dispatcher then moves results back and combines them.

Two flags pick the implementations code:

FlagDefaultPicks
--moe-a2a-backendnonehow tokens move between GPUs: deepep, mooncake, nixl, mori, pplx, flashinfer, and others
--moe-runner-backendautowhich grouped matrix multiply kernel runs the experts
--deepep-modeautonormal dispatch for prefill batches and low_latency dispatch for decode batches

With none, SGLang moves tokens with all-reduce or all-gather collectives. That works for any layout and costs more bandwidth at scale. The all-to-all backends send each token only where it must go.

The layout rules that SGLang enforces

The all-to-all backends span the whole TP group. When you choose one of them, SGLang sets --ep-size equal to --tp-size and logs the change at info level code. You cannot run DeepEP across four of eight GPUs. A mixed layout with expert parallelism smaller than tensor parallelism works only with none docs.

DeepEP has two dispatch modes. Normal mode sends large prefill batches with high throughput, and it cannot be captured in a CUDA graph. Low-latency mode sends small decode batches and works inside CUDA graphs. The default auto uses each mode where it fits. If you force --deepep-mode normal, SGLang turns off decode CUDA graphs and prints one warning line code. Section 4.1 shows what decode without graphs costs.

Choose the expert parallel size from your batch

Wider expert parallelism spreads experts thinner and moves more traffic over slower links. Ant Group measured this on H20 GPUs with DeepSeek-R1 decode field Ant-Group 2025-09:

They also chose EP16 to limit how many requests one failed GPU takes down. Their post appeared on the LMSYS blog, and the measurements are theirs.

Expert load balancing

Real traffic does not spread evenly over experts. Some experts get most of the tokens, and the GPUs that hold them become the slowest rank in every step.

EPLB: the expert parallelism load balancer. It records which experts each forward pass uses. Every --eplb-rebalance-num-iterations passes, 1000 by default, it computes a new placement and moves expert weights code. --ep-num-redundant-experts adds extra copies of popular experts, and its default is 0. A threshold flag skips the rebalance when GPU utilization is already high. Its default of 1.0 means that it never skips.

EPLB is off by default (--enable-eplb is false). Turn it on when your measurements show imbalance, not before. Run with --expert-balancedness-report-mode prometheus and watch sglang:eplb_balancedness code. The SGLang team reported EPLB speedups of 1.49 times for prefill and 2.54 times for decode team 2025-05. Those numbers came from a simulated imbalance, so expect less on traffic that is already balanced.

Overlapping communication with compute

Two-batch overlap (TBO): the scheduler cuts a batch into two micro-batches. One micro-batch runs attention while the other one waits on dispatch or combine. Turn it on with --enable-two-batch-overlap. It is off by default code.

For prefill, SGLang splits by token count. If no split puts at least 48 percent of the tokens on each side, it cuts one sequence across both halves. That is --tbo-token-distribution-threshold, 0.48 by default.

The SGLang docs say that TBO can "unlock up to 2x throughput" docs. The blog post that the docs link to measured 27 to 35 percent on 96 H100 GPUs team 2025-05. Plan for the measured number.

Ant Group turned TBO down on H20 field Ant-Group 2025-09. It helped only at batch sizes of 64 or 128, and at those sizes their time per output token missed its target. They used single-batch overlap instead, --enable-single-batch-overlap, which overlaps shared experts with the combine step. They measured 8 to 10 percent at batches of 20 to 56.

Our position

Turn on EPLB only after sglang:eplb_balancedness shows imbalance. Treat TBO as a throughput feature for large decode batches, and measure it against your time per output token before you keep it.

6.3

Prefill-decode disaggregation: --disaggregation-mode

Disaggregation moves prefill to its own servers so long prompts stop delaying other users' tokens, and it pays off only when that delay is your measured problem.

Your chat users see smooth streaming until someone pastes a long document. Then every stream pauses while the server prefills the document. Prefill is compute work on many tokens at once, and decode is one token per request per step. On one server, they share the same GPU steps, and the long prefill takes the step. Chunked prefill makes the pause shorter but cannot remove it.

When you finish this section, you can explain how SGLang moves a request's KV cache from a prefill server to a decode server. You can also start the smallest disaggregated setup and decide from measurements whether you need it.

Two servers, one request

Prefill-decode disaggregation (PD): two kinds of SGLang servers, started with --disaggregation-mode prefill and --disaggregation-mode decode. The default is null, which means one server does both code. A prefill server computes the prompt's KV cache and the first token. A decode server receives that KV cache and generates the rest.

The SGLang docs give two reasons for the split docs. Prefill batches interrupt decode batches. With attention data parallelism, one group can prefill while another decodes, so the decoding group waits for the slowest group in each step. Separate servers remove both kinds of waiting. Each pool can also use its own parallel layout, for example a wide TP for prefill and attention data parallelism for decode.

How the KV cache moves

The gateway in section 6.4 starts every exchange. It picks one prefill server and one decode server. It adds three fields to the request: the prefill server's bootstrap host, its bootstrap port, and a random 63-bit number called the bootstrap room. Then it sends the same request to both servers at the same time code.

Bootstrap room: the number that both servers use to find each other's half of one request. Think of it as a reservation number: the decode server books KV slots, and the prefill server writes into them.

  1. The decode server creates a receiver, finds the prefill rank through the bootstrap server, and reserves KV slots for the prompt.
  2. It sends the addresses of those slots to the prefill side.
  3. The prefill server runs a normal prefill forward pass for the prompt.
  4. It writes the KV pages into the decode server's reserved slots. With the default Mooncake backend, this is a one-sided RDMA write. Mooncake groups contiguous pages on both sides into one batch transfer code.
  5. The decode server sees the transfer finish and adds the request to its running batch without another prefill.
  6. The client stream comes from the decode server.

The bootstrap server runs on the prefill host. Its default port is 8998 code. Each side tracks a transfer with five states: Failed, Bootstrapping, WaitingForInput, Transferring, and Success code.

6.4

sgl-model-gateway and cache-aware routing

With several servers, the router decides your cache hit rate, so send each conversation back to the server that already holds its prefix.

You start a second server to double capacity. Throughput rises, but time to first token gets worse for long conversations. Each server has its own KV cache, and turn 5 of a chat goes to the server that never saw turns 1 to 4. That server prefills the whole history again. Section 3.4 measured what a prefix miss costs on one server. A router that ignores prefixes makes the same miss on purpose.

When you finish this section, you can explain how sgl-model-gateway picks a server for each request. You can also choose a routing policy for your traffic and check that the gateway keeps your hit rate.

Two places where requests get routed

SGLang routes requests in two places, with different defaults.

Inside one server: with --dp-size above 1, a data parallel controller gives requests to the copies. Its default method, auto, resolves to round_robin outside disaggregation code. Round robin ignores prefixes, as figure 6.1b shows.

In front of servers: sgl-model-gateway is a separate Rust program that routes to many SGLang servers. It was named sgl-router until pull request #14312 renamed it on 2025-12-05, for "less confusion". Its default policy is cache_aware code.

A field report shows the difference. Jarvislabs wrote that "SGLang's default routing deals each request to the next GPU in line, blind to where a conversation's cache lives" field Jarvislabs 2026-08. On their traffic, 23 percent of input tokens were computed again. One request header that pinned each conversation to one GPU raised their cache hit rate from 64.7 to 92.1 percent and halved median TTFT. Their post does not name the component that did the round robin. The in-server default matches their description.

How cache_aware picks a server

The gateway keeps one approximate radix tree per model. Each tree node records which servers have seen that prefix. The tree stores characters of the request text, not tokens, so the gateway never runs a tokenizer to route code.

Match rate: the number of characters of a new request that match the tree, divided by the request length.

For each request, select_worker does three things code:

  1. It checks balance. The system is imbalanced when two tests pass. The busiest server's load is more than 64 above the lightest, and more than 1.5 times the lightest. Then the request goes to the least-loaded server.
  2. Otherwise it computes the match rate. Above 0.3, the request goes to the server with the longest match.
  3. Below 0.3, the request goes to the least-loaded server, with a random choice among ties.

The gateway then inserts the request text under the chosen server. Every 120 seconds, a background task removes least recently used leaves until each tree is at most 67,108,864 nodes code.

A comment at the top of the policy file says that a low match goes to "the worker with smallest tree size". The code sends it to the least-loaded worker. The code wins, and this manual describes the code.

The tree is a guess

The gateway never asks a server what it caches. Its tree records where it sent text, and a server can evict that prefix later. So the gateway can send a request to a server that no longer holds its prefix. That request then prefills like any other miss. Check the hit rate on the servers, with sglang:cache_hit_rate from section 5.2, and not only the routing decisions.

Operating SGLang

Run SGLang so that a restart costs seconds and drops no request: pin the image, keep the compiled kernels, signal only the main process, and tune in a measured order.

The first production incident with a new serving engine is rarely about tokens per second. A rolling update kills ten requests in the middle of their answers. A new pod takes four minutes to become ready, so the autoscaler starts three more. A liveness probe times out under load and restarts the busiest pod. None of these appear in a benchmark, and all of them cost more than a slow kernel.

Health checks: /ready, /health, and /health_generate

SGLang has two kinds of health endpoint code:

  • /ready returns 200 when the tokenizer manager is ready and 503 before that.
  • /health and /health_generate share one handler. They return 503 while the server starts and while it shuts down.
  • Otherwise the handler sends a one-token request with max_new_tokens 1 and waits for any output from the detokenizer.
  • SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION defaults to true, so a plain /health also generates that token.
  • The wait is SGLANG_HEALTH_CHECK_TIMEOUT, 20 s by default. With no output in that time, the handler marks the server UnHealthy and returns 503.

The docstring says that the probe request costs nothing when the server is busy, because any output from the scheduler counts as proof of life. That is true for the work, and false for the timing. A real incident: issue #22511 reports "health check failed. server could not get a response from detokenizer for last 20 seconds" on GLM-5 with 2 H800 GPUs under high load, on v0.5.10 issue #22511. A related issue, #35884, found that a timed-out probe left its request in the scheduler, so failed probes accumulated issue #35884.

Our position: use /ready for the readiness probe. Keep the liveness probe from generating. Set SGLANG_ENABLE_HEALTH_ENDPOINT_GENERATION=false, and /health then returns 200 without a request to the scheduler code. Use /health_generate for a slower deep check that alerts a person and restarts nothing. A busy server then does not lose its busiest pod to a probe that waited in the queue.

On SIGTERM, the HTTP server sets gracefully_exit, and /health starts to return 503. A watchdog in the tokenizer manager checks the flag every 5 s code. It then logs the remaining requests every 5 s until none remain. Then it sends ShutdownReq to the schedulers and gives them 15 s to exit before it kills them. The code has two exits that skip the drain. If the server is already UnHealthy, the watchdog exits at once. It also exits at once if the environment variable SGL_FORCE_SHUTDOWN is true. At v0.5.22 the watchdog reads that old name directly code.

The code shows that setting only SGLANG_FORCE_SHUTDOWN does not reach the watchdog. We read this in the code and did not run it, so we call it a likely bug. If you need a forced stop, set SGL_FORCE_SHUTDOWN=1.

Our position: set the termination grace period longer than your longest request at your output cap. A 32K-token answer at 30 tokens per second needs more than 18 minutes. Cap max_tokens before you set the grace period, or a drain can never finish in time.

Most tuning advice lists flags. The order matters more than the list, because each step changes what the next step measures. Figure 7.1b shows the order this manual uses, and each row links to the section that measures it.

7.2

SGLang as an RL rollout engine

In reinforcement learning the server becomes part of the training loop, so its memory, its weights, and its log probabilities all become the trainer's problem.

You train a model with GRPO. Every step, an inference server writes thousands of answers, a reward function scores them, and the trainer updates the weights. Then the server must answer the next prompts with the new weights, on the same GPUs that the trainer just used. A serving engine built for chat never had to give its memory back or change its weights while it runs. It never had to match another program's numbers to the last bit.

When you finish this section, you can describe one RL step with SGLang as the rollout engine and name the SGLang endpoints each phase calls. You can also choose a weight transfer method and say what "true on-policy" covers and what it does not. The example is Miles v0.1.2 (commit a22fd824), the RL framework that RadixArk maintains next to SGLang.

The receipt for training on stale numbers

Miles is a fork of slime, an RL framework from THUDM, and keeps slime's history. RadixArk describes it as "Enterprise-Grade Reinforcement Learning for Large-Scale Model Post-Training". The docs never define "enterprise". In the code it means three things: correctness checks between rollout and training, recovery from engine faults, and observability.

Each of those exists because RL changes what an inference server is. The server's output is the training data. The log probabilities it reports are the "old policy" in the PPO and GRPO ratio. So any numerical difference between SGLang kernels and the trainer's kernels becomes a bias in the gradient. Miles is the receipt for training on numbers that the server did not produce.

The loop that borrows the server

The training driver is short on purpose. At v0.1.2, train.py has 175 lines. These are the lines of one step when the trainer and SGLang share GPUs:

Read it as a rental. SGLang generates and scores the rollout. SGLang releases its CUDA graphs, KV cache, and weights. The trainer loads, trains, and offloads itself. SGLang gets its weights back, receives the new weights, and then gets its KV cache and CUDA graphs back. Figure 7.2b shows which memory is on the GPU in each phase.

What stock SGLang gives the trainer

The rental works through SGLang HTTP endpoints that exist in stock v0.5.22 code. SGLang's RL guide states the design rule as "Be a library, not a framework" docs. Miles drives each engine as an ordinary sglang serve process over HTTP.

Memory release: POST /release_memory_occupation frees GPU memory by tag, and POST /resume_memory_occupation gives it back. The server needs --enable-memory-saver, which is off by default. The tags are kv_cache, weights, and cuda_graph. The docs list only the first two, and the code accepts all three, so the code wins. The memory saver frees physical memory but keeps the virtual addresses, so captured CUDA graphs stay valid without a new capture. The call asserts that the server is idle, so pause generation first.

Pause and resume: POST /pause_generation takes a mode. SGLang's default is abort, which ends every running request. Miles uses retract by default, which puts running requests back in the waiting queue so they prefill again after the update. A third mode, in_place, keeps their KV cache from the old weights.

The weight-update session: begin_weight_update, then one or more update_weights_from_* calls, then end_weight_update. The session exists because quantized layers need a one-time repack after loading. Doing it once per refit is cheaper than once per bucket. After the session, update_weight_version stamps the new version. A request that lived through a refit reports weight_versions spans in its meta_info, so you can see which tokens came from which weights. Figure 7.2 shows one update with the default transfer.

Miles picks the transfer with --update-weight-transfer-mode code:

With --colocate, Miles ignores this flag and always sends CUDA IPC handles through /update_weights_from_tensor. A team that sets p2p on a colocated run measures the wrong thing and never knows.

The Miles team reports P2P timings on H100 clusters with a 1 GB bucket team 2026-10. Qwen3-235B-A22B on 8 nodes went from 10,754 ms with NCCL broadcast to 3,162 ms, 71% less. Kimi-K2 on 32 nodes went from 53,279 ms to 7,227 ms, 86% less. On one node P2P was slower: GLM-4.7-9B-Flash took 68.6% longer and a 4-layer GLM-5 test took 72.2% longer. The reason is in the design. Broadcast sends the full model to every engine rank, and with expert parallelism each rank needs only a fraction of it.

RadixArk reports that about 2% of BF16 parameters change in one step team 2026-08. For GLM-4.7-Flash the disk-delta payload fell from 62.4 GB to 0.69 to 0.83 GB per update, with a generation pause of 3 to 5 s. These are their numbers from the Miles v0.1 post of 2026-08-18. We did not reproduce them.

Our position: start colocated on one node with the CUDA IPC path. Move to separate GPUs only when rollout time dominates the step. Choose p2p only for multi-node MoE, where the vendor table shows the gain, and keep broadcast everywhere else.

True on-policy, and where it stops

Here the serving engine and the trainer must agree on a number. Give SGLang and Megatron or FSDP the same weights and the same tokens. Their kernels can still return different log probabilities, because their reductions run in a different order. Then the PPO ratio mixes "the policy changed" with "the kernels differ". Miles reports the gap as train/train_rollout_logprob_abs_diff, which should be exactly 0 in true on-policy mode.

Two SGLang facts matter first. SGLang returns log probabilities after temperature scaling unless the request is greedy or SGLANG_RETURN_ORIGINAL_LOGPROB is set, as section 4.6 explains. A trainer that compares at temperature 1 sees a mismatch that no kernel causes. Second, --rl-on-policy-target accepts one value at v0.5.22, fsdp, and it forces deterministic inference code. That mode replaces matrix multiply, softmax, and norm kernels with batch-invariant versions and forces the PyTorch sampler. It also turns off the radix cache unless the attention backend is fa3, fa4, triton, or ascend.

Miles builds on that with a launch plan that sets matching flags on both sides. The coverage is narrow. At v0.1.2 the only model profile is Qwen3 dense: Qwen3-0.6B, Qwen3-4B, Qwen3-4B-Base, and Qwen3-4B-Instruct-2507. Three open issues in the Miles repository show where bitwise parity still breaks:

  • Issue #1485: Qwen3-4B down_proj outputs differ at tensor parallel 2. SGLang sums 38 partial results in two groups of 19, and Miles sums them in a pairwise tree. BF16 addition is not associative issue radixark/miles#1485.
  • Issue #3714: deterministic serving pins the NCCL channel limit to 8 while the trainer uses 24. Weight transfer then fails with Message truncated : received 6144 bytes instead of 2048 issue radixark/miles#3714.
  • Issue #3277: after a retract, re-prefill under the new weights overwrites the recorded MoE routes. The response then carries new routes with old log probabilities issue radixark/miles#3277.

Our position: treat true on-policy as a diagnostic for Qwen3 dense models, not a switch for every run. Log the log-probability gap on every run anyway. A large gap means a conversion or kernel problem, and no RL algorithm fixes that.

Miles runs on its own SGLang

Miles does not use the SGLang release that the rest of this manual describes. Its Docker image builds on lmsysorg/sglang:v0.5.21 and checks out the sglang-miles branch. The v0.1.2 release lock pins SGLang commit b84bec5761a6. The Miles docs say it plainly: "installing stock sglang or upstream Megatron-LM next to Miles does not work." docs

At least four things that Miles calls do not exist at v0.5.22: the /pull_weights endpoint for disk-delta, register_lora_adapter, get_parallelism_info, and the --true-on-policy-contract flag.

That branch is a fair summary of this section. RL asks a serving engine for things that serving users never asked for. It must give memory back and change weights in a session. It must report which weights produced each token and match another program bit for bit. Some of those requests are now in stock SGLang. The rest live on a branch until they are ready.

A real incident: issue #860 in the Miles repository reports that /release_memory_occupation "silently does nothing" for models with sliding-window attention issue radixark/miles#860. The sliding-window KV pool turns the memory saver off in its constructor, so a colocated run runs out of memory when Megatron starts. One user saw 30.19 GB of KV pool stay resident on DeepSeek-V4-Flash. The issue was open on 2026-10-16. Check that every memory tag really frees memory on a new model before you trust colocation.

What to do with this
  • Pin the Miles image and its release lock, and never mix a stock SGLang into it.
  • Pause generation before you release memory, because the release asserts an idle server.
  • Start colocated on one node, and expect --colocate to override the transfer mode.
  • Choose p2p only for multi-node MoE runs, and measure the update time first.
  • Log the rollout and training log-probability gap on every run.
  • Set SGLANG_RETURN_ORIGINAL_LOGPROB when your trainer compares at temperature 1.
  • Treat true on-policy as a Qwen3 dense diagnostic at v0.1.2.
