How to read this manual

Every listing in this manual comes from one recorded run of rea 6.5.0 with Ghidra 12.1.4 on programs written for it, and every rule traces to a ranked source.

This manual explains rea, the rea-agents package at version 6.5.0, with the Ghidra 12.1.4 provider. It follows one question from a file you compiled to an Evidence record you can check. The question is what a function does, and how the tool knows.

Who this manual is for

You write C, Python, or JavaScript, and you use a coding agent such as Claude, Cursor, Codex, OpenClaw, Hermes, or any agent that reads SKILL.md. You have never read machine code with a decompiler, and you want to check what an agent tells you about a compiled program.

After the last part, you can:

  • Read the file header, sections, symbols, and relocations of a compiled program, and map an address to a file offset.
  • Run rea with the Ghidra provider on a program you built, and read its Evidence record: confidence, authority, limitations, and unknowns.
  • Find a function, read its assembly and pseudocode, follow its references, and say where the decompiler output is incomplete.
  • Prove a rebuilt function equal to the original by running both over an input grid and by comparing bytes after masking relocations.
  • Drive rea from an agent over MCP, and keep an evidence ledger that separates what was observed from what was inferred.

Five lessons go deeper than rea does. The ELF lesson builds a file reader. The disassembly lesson builds a decoder and a control-flow graph. The lifting lesson builds a lifter. The evidence lesson builds a ledger, and the proof lesson proves a rebuild equal. This manual stays with rea and Ghidra.

Conventions

rea names the 6.5.0 command line in every command. The kit started it from the npx cache as node .../node_modules/rea-agents/scripts/rea.mjs, and rea mcp names the MCP server of the same package.

$CAPTURE stands for the capture directory, $OUT for capture/out/, $WORK for the kit's work directory, and $HOME for the home directory. Values that change on every run appear as tokens such as <hash> and <ts>. Addresses are lowercase 0x hexadecimal, as rea prints them. _percent_change with a leading _ is the Mach-O symbol, and percent_change is the C name and the ELF symbol.

Citations name a place. {{cli Choose a provider}} names a heading in a rea documentation page at the tag, and {{readme}} names the README. The rea source files a section was written from are listed once, in the Sources line at its end, at the tag. A capture path, such as capture/out/06-function-percent-change.json, names the recorded file. A listing copies lines from a capture file unchanged, and a … marks a cut that the note explains.

1.1

rea, providers, and Evidence

rea standardizes the question, the session, and the Evidence record, and leaves import, analysis, and decompilation to the engine it binds, here Ghidra 12.1.4.

You compiled ledger.c with clang -O1, and you want to know what the machine code of percent_change does when before is 0. You can open the file in Ghidra and read the listing yourself. You can also ask rea, and rea asks Ghidra for you and returns one record that says what it found and how it knows. This section draws the line between the two programs.

When you finish this section, you can name what rea adds to Ghidra, what it never does, and which adapter to use for one question.

Three things rea standardizes

Evidence: the one record type that every successful analysis call returns. It is a strict object with 16 fields. The fields are evidence_id, subject, provider, analysis_profile, predicate_type, operation, parameters, raw_result, normalized_result, confidence, authority, environment, limitations, relationship_coverage, locations, and evidence_links.

The id is ev_ and a SHA-256 of the semantic content. The same observation of the same bytes gets the same id on any machine. When relationship_coverage is null, the id leaves it out. confidence is one of observed, derived, or inferred, and authority says what kind of source backs the fact.

The MCP docs state the rule for tools: "Evidence-producing tools return the complete canonical Evidence record in both text and structured content." mcp Tool results. Section 1.2 reads one record field by field, and Part 5 covers the record in full.

Provider: an analysis engine behind one interface. GhidraProvider implements AnalysisProviderCandidate and offers identity(), capabilities(), inspectAvailability(), inspectTargetSupport(target), resolveAnalysisProfile(...), and createClient(...). At 6.5.0 the session holds three deep providers, hopper, ghidra, and ida, plus auxiliary providers that need no engine. The registry sorts candidates by id and selects one without starting it, and "Registration order never affects selection or caller-visible output". Once bound, a provider stays bound: "A selected provider is never replaced automatically after a runtime failure." mcp Identity and discovery.

Adapter: the way a caller reaches the session. The one-shot CLI has 153 commands and one alias, and the MCP server has 207 tools and 6 prompts. The capture's server_identity.catalog.counts reports those numbers (capture/out/02-capabilities.json). Both adapters share one BinarySession, which "Owns the single active target shared by CLI and MCP adapters". CLI names use hyphens and MCP names use _ between words. The native family breaks the rule: rea function calls analyze_function, rea decompile calls procedure_pseudo_code, and rea analyze calls binary_overview.

What rea leaves to Ghidra

rea has no disassembler and no decompiler of its own. For a native executable it starts analyzeHeadless on a fresh temporary project and imports a private copy of the file. It lets Ghidra's default auto-analysis run, and then it asks questions over a socket. The answers are Ghidra's. The function dossier "combines Ghidra FunctionManager, Listing, ReferenceManager, BasicBlockModel, and decompiler observations", as every analyze_function record says in its limitations (capture/out/06-function-percent-change.json). The provider docs draw the same line: "pseudocode is Ghidra decompiler output. Neither is original source" ghidra Admitted function-analysis semantics.

Bridge: ReaGhidraBridge.java, a GhidraScript that analyzeHeadless runs as its last post-script and that then serves requests on a Unix socket. A request is one JSON line, { id, token, method, params }, and a reply is { id, ok: true, result } or { id, ok: false, error }. The bridge answers 16 inventory methods and 13 function methods through one Java switch. Part 4 follows each of them.

Ghidra also owns the cost. Each one-shot command that needs Ghidra took 7 to 9 s on the capture Mac (capture/README.md, capture/out/00-commands.txt). The import and the auto-analysis take most of that time. Inside one MCP session the first Ghidra call took 5 to 7 s (capture/README.md, capture/out/10-mcp-session.txt). Every later call on the same file took under 100 ms.

What rea reads by itself

Before any engine runs, rea reads the file. It detects ELF from 7f 45 4c 46, MZ, and the four Mach-O magic values. It hashes every target with SHA-256 in 64 KiB chunks. It knows eight architectures: x86, x86_64, arm, arm64, mips, 6502, riscv, and powerpc. A raw binary has no header, so the caller names its architecture.

Two commands show the result without Java. rea inspect-artifact walks the file with the provider rea-artifact-graph and returns an Evidence record in under a second, without Java (capture/out/03-inspect-artifact.json). On macOS, rea inspect-macho runs the Xcode tools through xcrun and took about three seconds (capture/out/04-inspect-macho.json). Part 3 reads those records.

Formats beyond native code

Release 6.5.0 adds three readers. inspect-wasm-artifact reads a WebAssembly module through the WABT tools. inspect-go-binary reads Go build information. The raw-binary format opens a file that has no header, at an architecture that you name. The capture ran inspect-wasm-artifact on the fixture module, and the command exited 0 (capture/out/16-inspect-wasm-artifact.json). Section 6.2 reads that record.

What to do with this
  • Ask rea for an Evidence record, and read Ghidra's own listing when you doubt it.
  • Use the CLI for one question and the MCP server for a session of many.
  • Treat the 16 fields as the contract, and the dossier inside normalized_result as Ghidra's answer.
  • Expect 7 to 9 s for the first Ghidra question on a file, and milliseconds after it.

rea function, end to end

One rea function call opens the file, binds Ghidra, imports a private copy, asks one question over a socket, and prints one Evidence record in about eight seconds.

You typed rea function fixtures/ledger-arm64-O1 _percent_change --provider ghidra --format json. About eight seconds later, 1881 lines of JSON arrived on stdout, and the exit status was 0. Somewhere in there is the answer to your question about before == 0, next to a decompiler artifact that the source never had.

When you finish this section, you can read every top-level field of that record and say which part of the system wrote it. You can also point at the one place where Ghidra's pseudocode and your C disagree.

The command

function takes a path and a procedure, and it runs the MCP operation analyze_function with { procedure } as its parameters. --provider ghidra names the engine, and --format json and --filter-output are read at the executable boundary before the command runs. Without --format, the terminal output is TOON, and exit 0 means "The operation completed. Its result may include partial evidence, warnings or unresolved questions." cli Output and exit status. Figure 1.2 follows the call through the system.

From the command to the bridge

  1. The session parses the Mach-O header, reads the architecture, and hashes the file. The record's subject carries the result: mach-o, arm64, and the SHA-256 that 00-fixtures.txt lists for ledger-arm64-O1.
  2. The registry selects ghidra, because the command asked for it, and records selection_source: "request".
  3. The provider builds the analysis profile, a list of versioned contract names such as function_body_evidence: "complete-inclusive-ranges-v1", and hashes it. The digest 966e6016… in the record is this hash.
  4. The client makes a private runtime root and allocates bridge.sock. It copies the file as target-<sha256[0:12]>.bin while hashing it again. Then it launches java with ghidra.Ghidra ghidra.app.util.headless.AnalyzeHeadless, -import, -readOnly, and -deleteProject. The copy is target-01b5d08b08fb.bin, and the overview record shows that name as its document (capture/out/05-analyze-arm64-O1.json). The startup deadline is 330,000 ms.
  5. The client sends ping. It accepts the session only when run_id, the token, the profile digest, the target SHA-256, and analysis_complete all match.
  6. The client writes one JSON line that asks for analyze_function. Ghidra runs the analysis and writes one JSON line back.
  7. rea adds the operation's limitation sentences to the answer and stores the result as one Evidence record.
  8. The client sends shutdown with a 10 s deadline, and Ghidra deletes the project.

The record, field by field

evidence_id hashes the semantic content and leaves out subject.name and subject.local_path, so the same bytes under another path give the same id. provider names the engine and its version. The next field binds the answer to the engine's settings:

Analysis profile: the provider's committed settings, hashed over RFC 8785 canonical JSON. Change one contract version and the digest changes, which is how rea refuses an old snapshot (section 5.3). predicate_type is the default tag rea.analysis, and operation is the MCP name. parameters is the caller's input, and it is part of the identity.

raw_result holds the provider-native dossier under value with its own empty limitations, and normalized_result holds the same dossier as the canonical result. confidence is observed and authority is shipped-artifact, the defaults for a static read of the file on disk. environment is null, because nothing ran.

limitations has ten strings: four that every Ghidra operation carries, five for analyze_function, and one for macOS about the native decompiler (capture/out/02-capabilities.json, 06-function-percent-change.json). locations and evidence_links are empty. relationship_coverage has the status complete, and its one diagnostic says that only resolved Ghidra call references are returned. Figure 1.3 lays the 16 fields out.

Inside normalized_result

Procedure: the function identity. _percent_change is at 0x100000500, its body is one range from 0x100000500 to 0x100000517 inclusive, 24 bytes, and contains_entry is true. The FunctionManager signature reads undefined _percent_change(), because Ghidra's symbol carries no types. The decompiler's view under native_api reads ulong _percent_change(ulong param_1,int param_2) with confidence: "low" on each parameter. Your source says int percent_change(int before, int after). Both are observations, as the limitation says: "Types and calling conventions are Ghidra decompiler observations, not source declarations."

Six instructions of four bytes each make the 24 bytes. cbz w0 is your if (before == 0) return 0;, with before in w0, and mov w9, #0x64 is the 100. The pseudocode tells a longer story:

The outer if is your guard. The inner if is not in your source. native_value_flow shows where it comes from. The operations 0x100000510#7, #8, #9, and #10 are a COPY of the constant 0, an INT_NOTEQUAL, a CBRANCH, and an INT_SDIV. All four carry the address of the sdiv instruction. Ghidra's model of sdiv gives 0 when the divisor is 0, and the decompiler printed that model as a second check.

Both checks are correct, and one is redundant, and only the source tells you which. Section 4.6 and the lifting lesson go deeper.

References: the dossier lists two incoming references. One is an UNCONDITIONAL_CALL from 0x1000006a0 inside the function Ghidra names entry at 0x1000005d0, 368 bytes long. The other is a DATA reference from 0x100008118 with no owning procedure, inside the __LINKEDIT segment that the overview lists from 0x100008000 (capture/out/05-analyze-arm64-O1.json). The one outgoing reference is the CONDITIONAL_JUMP of cbz. callers names entry, and callees is empty, because the function calls nothing. unresolved_calls is empty, and facet_availability marks all eight facets of the dossier as available.

Basic blocks: three, at 0x100000500, 0x100000504, and 0x100000514, with exclusive end values. The body range uses inclusive ends, as its contract name complete-inclusive-ranges-v1 says. Keep the two conventions apart when you compare addresses.

native_value_flow holds 13 p-code operations and 13 def-use edges with truncated: false. Every operation carries is_dead: true, and the limitation explains that the flag mirrors the Java AST and that block_membership reports the real membership. Read the limitations before the numbers, every time.

What to do with this
  • Run rea function PATH NAME --provider ghidra --format json and save the whole record.
  • Check subject.digest.sha256 against your own shasum -a 256 before you trust anything else.
  • Read confidence, authority, and limitations before normalized_result.
  • Compare the pseudocode with the assembly, and expect decompiler checks that the source never had.

The README use rule and the law

You analyze a program only when you have the right to, and in this manual that right comes from writing every target yourself.

A vendor sent you a binary, and an agent at your side can decompile it in eight seconds. Before the first command, two questions stand. Who owns the program, and what does the law allow you to do with a copy you did not write? rea asks neither question. Its DISCLAIMER.md puts the answer on you, and the statutes and decisions below say what the answer has to contain.

When you finish this section, you can say which rule lets you analyze a program, and why every target in this manual passes that test. This section reads primary sources and gives no legal advice.

The use rule at the tag

the use rule
"You are responsible for obtaining any required authorization and for complying with applicable laws, license agreements and terms of service. Reverse engineering may be restricted in your jurisdiction or by the license of the software you analyze."
readme DISCLAIMER.md, Responsible use

The rule is a paragraph under the heading Responsible use in DISCLAIMER.md at the tag. The README has a Disclaimer heading that sends you to that file. It also says: "REA is for lawful research, education, interoperability, software preservation, and analysis of software you own or are authorized to examine." readme Disclaimer It adds that this position covers all REA versions and distribution channels.

DISCLAIMER.md also lists the uses that the project does not support. The first item is the circumvention of DRM, licence checks, anti-cheat systems, and other protection measures. Then come game cheats, the bypass of authentication or access controls, and copies of proprietary software. The last two items are the evasion of AI provider usage policies and the resale or sharing of AI accounts.

United States: 17 U.S.C. 1201

Circumvention: under 1201(a)(3)(A), "to descramble a scrambled work, to decrypt an encrypted work, or otherwise to avoid, bypass, remove, deactivate, or impair a technological measure, without the authority of the copyright owner" law 17 U.S.C. 1201(a)(3)(A). Section 1201(a)(1)(A) forbids it.

Section 1201(f) is the reverse engineering exception, and it stacks four limits. The person must have "lawfully obtained the right to use a copy of a computer program". The circumvention must be "for the sole purpose of identifying and analyzing those elements of the program that are necessary to achieve interoperability of an independently created computer program with other programs". Those elements must "have not previously been readily available to the person". The acts must not "constitute infringement under this title" law 17 U.S.C. 1201(f)(1).

Section 1201(f)(4) defines the key word: "the term 'interoperability' means the ability of computer programs to exchange information, and of such programs mutually to use the information which has been exchanged." law 17 U.S.C. 1201(f)(4). Section 1201(j) covers security testing, which it defines as "accessing a computer, computer system, or computer network, solely for the purpose of good faith testing, investigating, or correcting, a security flaw or vulnerability, with the authorization of the owner or operator" law 17 U.S.C. 1201(j)(1).

Section 1201(f) is an exception to the anti-circumvention rule only. It does not decide whether the copies you make while analyzing infringe copyright. Section 1201(c)(1) leaves that question to copyright law: "Nothing in this section shall affect rights, remedies, limitations, or defenses to copyright infringement, including fair use" law 17 U.S.C. 1201(c)(1). The two decisions below answer it.

European Union: Directive 2009/24/EC

Article 1(2) sets the ground: "Ideas and principles which underlie any element of a computer program, including those which underlie its interfaces, are not protected by copyright under this Directive." law Directive 2009/24/EC Article 1(2). Two articles then give a lawful user two rights.

Article 5(3) is the right to study a running program: "The person having a right to use a copy of a computer program shall be entitled, without the authorisation of the rightholder, to observe, study or test the functioning of the program in order to determine the ideas and principles which underlie any element of the program if he does so while performing any of the acts of loading, displaying, running, transmitting or storing the program which he is entitled to do." law Directive 2009/24/EC Article 5(3). The Court of Justice applied it in C-406/10. There a licensee studied the SAS System to reproduce its functionality in a second program, without decompilation, and did not infringe.

Article 6(1) is the decompilation right. It needs no authorisation "where reproduction of the code and translation of its form within the meaning of points (a) and (b) of Article 4(1) are indispensable to obtain the information necessary to achieve the interoperability of an independently created computer program with other programs" law Directive 2009/24/EC Article 6(1). Three conditions follow. First, the acts are done by a person with a right to use a copy. Second, "the information necessary to achieve interoperability has not previously been readily available" law Directive 2009/24/EC Article 6(1)(b). Third, "those acts are confined to the parts of the original program which are necessary in order to achieve interoperability" law Directive 2009/24/EC Article 6(1)(c).

Article 6(2)(c) then forbids using the result "for the development, production or marketing of a computer program substantially similar in its expression" law Directive 2009/24/EC Article 6(2)(c). A contract cannot take these rights away. Article 8 says: "Any contractual provisions contrary to Article 6 or to the exceptions provided for in Article 5(2) and (3) shall be null and void." law Directive 2009/24/EC Article 8. In C-13/20 the Court added a third route. A lawful purchaser can decompile to correct errors under Article 5(1), without the Article 6 conditions, but "only to the extent necessary to effect that correction" law C-13/20 ruling 2.

Two decisions: Sega v. Accolade and Sony v. Connectix

In Sega Enterprises Ltd. v. Accolade, Inc., 977 F.2d 1510 (9th Cir. 1992), Accolade bought a Genesis console and cartridges, disassembled the object code, wrote a manual of interface requirements, and then wrote its own games. The court held: "where disassembly is the only way to gain access to the ideas and functional elements embodied in a copyrighted computer program and where there is a legitimate reason for seeking such access, disassembly is a fair use of the copyrighted work, as a matter of law." law Sega v. Accolade, 977 F.2d at 1527-1528. The only code Accolade kept was a header of 20 to 25 bytes that the console required.

In Sony Computer Entertainment, Inc. v. Connectix Corp., 203 F.3d 596 (9th Cir. 2000), Connectix copied the PlayStation BIOS into memory many times while it built an emulator that contained none of Sony's code. The court held: "The intermediate copies made and used by Connectix during the course of its reverse engineering of the Sony BIOS were protected fair use, necessary to permit Connectix to make its non-infringing Virtual Game Station function with PlayStation games." law Sony v. Connectix, 203 F.3d 596.

The court listed four ways to reach the functional elements of a program. Two of them are the static examination of the instructions and the dynamic examination of a running program, and it called both disassembly. Both decisions protect the intermediate copies and say nothing about copied code in the finished product.

The command

The arithmetic from the load command

File offset: the position of a byte in the file, counted from zero. Virtual address: the position of the same byte in memory after the loader maps the segment that contains it. A segment maps filesize bytes starting at fileoff to vmsize bytes starting at vmaddr, so inside one segment the two positions differ by a constant.

From the previous section, __TEXT has vmaddr 0x100000000 and fileoff 0. The rule for any byte in that segment is offset = address - vmaddr + fileoff. For _grade, that is 0x100000518 - 0x100000000 + 0, which is 0x518, which is 1304.

The section gives a second check. __text has address 0x100000500 and file_offset 1280. The function starts 0x18 bytes, 24 bytes, after the section, so its offset is 1280 + 24, again 1304. Open the fixture at byte 1304 and you find e8 cc 8c 52. That is the little-endian encoding of mov w8, #0x6667, the first instruction of _grade in section 4.3.

open_binary and the headless bridge

open_binary binds one target to one provider in milliseconds, and the first Ghidra-backed call pays for a headless import, auto-analysis, and a private socket.

Your agent opened ledger-arm64-O1 over MCP in a few milliseconds and then waited several seconds for list_procedures. Nothing was wrong. The open call did not start Ghidra. The first question did, and every question after it came back in milliseconds.

When you finish this section, you can read the server log of a session and name the process that the first query started. You can also predict which calls will be slow.

open_binary

The handler calls session.open with the path and the provider id, then returns five fields: path, format, kind, sha256, and architecture. To fill them rea reads the magic bytes: 7f 45 4c 46 for ELF, MZ for DOS and PE, and four Mach-O values. It hashes the whole file in 64 KiB chunks. A file with no header needs an explicit format. With format: "raw-binary" you also give architecture and entry_point, and the result adds entry_point. rea refuses a WebAssembly module here and sends it to inspect_wasm_artifact. For every other target, rea selects the provider you asked for, and binary_session records that choice.

selection_source: "request" says the agent chose Ghidra. The profile digest is the one every Ghidra record of this target carries. The docs state the limit of the open call in one sentence:

what open_binary does not do
"open_binary then selects a target and provider binding; it does not establish that Ghidra has finished importing the target."

The first Ghidra-backed call

The capture kit records the pattern in its README. The first Ghidra-backed call after open_binary takes 5 to 7 s. Every later call on the same target takes under 100 ms. The difference is the Ghidra start. GhidraClient.callTool awaits start() before it queues any request, so the first call pays for the whole sequence in #startWithin:

  1. Create a private runtime root named rea-ghidra- and a random suffix under the session root.
  2. Allocate the endpoint, a Unix socket on macOS and Linux.
  3. Copy the target into the root as target-01b5d08b08fb.bin, hashing while copying, and refuse a digest mismatch.
  4. Mint a 32-byte random token and a run id.
  5. Write session.json with transport, endpoint_path, token, run_id, target_sha256, provider_version, and profile_digest.
  6. Start Java and wait for the bridge to accept a connection.

Headless import: a Ghidra run with no window that imports one file into a project and runs the default analyzers. On macOS and Linux, rea does not run the analyzeHeadless shell script. It asks Ghidra's LaunchSupport.jar for the environment and the JVM arguments, then runs java itself. The heap is -Xmx2G unless GHIDRA_HEADLESS_MAXMEM or GHIDRA_MAXMEM is set. The command adds -Djava.awt.headless=true and names the class ghidra.Ghidra with ghidra.app.util.headless.AnalyzeHeadless. The docs give the reason: "Apple platform shell wrappers hide their environments from ownership inspection, so retaining those wrappers would prevent verified process-group cancellation during startup." install §Ghidra

The headless arguments come in one fixed order:

  • the project root and the project name rea-project
  • -import with the copied target
  • -readOnly and -deleteProject
  • -log and -scriptlog into the runtime root, and -scriptPath at the bridge directory
  • -postScript ReaGhidraNoReturnFix.java
  • -postScript ReaGhidraBridge.java with the path of session.json, last

Some targets and settings need more arguments. A raw binary, a DOS file, or a language override adds a loader and a processor. Seeds and disabled analyzers add pre-scripts. The fixtures of this manual need none of them.

The bridge on the Java side

ReaGhidraBridge.java is a Ghidra script that runs after the import and the analyzers. Its run() reads session.json and deletes it, then requires an imported program. It checks that the Ghidra version equals provider_version and compares the program's own SHA-256 with target_sha256 in constant time. It then ends the script transaction, initializes the decompiler, and serves. On a Unix socket it binds the path, sets the mode to rw-------, and accepts one client.

Each request is one JSON line, { id, token, method, params }. Each reply is { id, ok: true, result } or { id, ok: false, error: { code, message } }, and rea parses it with a strict schema. list_procedures was request number 2 on that socket, after the ping of the handshake, and it took the Java side a few milliseconds. The seconds before it were the import and the analyzers.

Deadlines and the close

rea allows 330,000 ms for the start, set by REA_GHIDRA_STARTUP_TIMEOUT_MS. On the capture Mac the start took 5 to 7 s, and the client limit is the one to watch: "The pinned client SDK 2.3.1 defaults to 60,000 ms and can cancel earlier than REA's startup deadline." mcp §Ghidra first-query deadlines and recovery

The docs record about 64 s on a Linux fixture and about 163 s on Windows. Set the client deadline from your own first run on your own machine.

close_binary takes a fraction of a second in the log. The client sends shutdown to the bridge with a 10 s limit, the bridge disposes the decompiler, and -deleteProject removes the project. The next open_binary on ledger-arm64-O2 took about a millisecond, and its first analyze_function again took seconds, because "Each new provider session still imports the target into a fresh temporary project." mcp §Ghidra first-query deadlines and recovery

What to do with this
  • Expect the first Ghidra-backed call after open_binary to take seconds and the rest milliseconds.
  • Set the MCP client deadline from a measured cold start on your own machine.
  • Ask every question you have before close_binary, because the project is deleted.
  • Read durationMs in the server log to separate rea time from Ghidra time.

procedure_assembly

procedure_assembly returns the Ghidra Listing text of one function as a string, one instruction per line, with the address first and no bytes.

You want to see the division by ten in grade as the processor sees it. The C source says score / 10. The arm64 code has no divide instruction at all, and reading why is the first thing assembly teaches.

When you finish this section, you can read the 15 instructions of _grade, split them into three blocks, and explain the multiply by 0x66666667.

The call and the text

The bridge resolves the procedure, scans its instructions with no limit, renders each one as text, and attaches any no-return call warnings. The record carries the limitation "Assembly is Ghidra Listing text and does not claim textual equivalence with Hopper output.". The text is Ghidra's rendering, so register names, immediates, and spacing follow Ghidra, not clang or llvm-objdump.

The dossier of section 4.6 carries the same lines as an array, which is easier to read.

Reading the fifteen instructions

The argument score arrives in w0, the low 32 bits of x0, and the result leaves in w0. Read the text in four groups.

The first two lines build a constant. mov w8, #0x6667 sets the low half, and movk w8, #0x6666, LSL #16 inserts the high half, so w8 is 0x66666667.

The next four lines divide by ten without a divide. smull x8, w0, w8 multiplies the two 32-bit values into a 64-bit product. asr x8, x8, #0x22 shifts the product right by 34, and lsr x9, x8, #0x3f takes its sign bit. add w8, w8, w9 adds the sign bit, which corrects the rounding for a negative score. The result is score / 10 with C truncation. Lesson 34 proves that 0x66666667 and a shift of 34 give that quotient for every 32-bit int.

The next three lines are the switch. sub w8, w8, #0x6 turns the cases 6 to 10 into the indexes 0 to 4. cmp w8, #0x4 and b.hi 0x10000054c send any index above 4 to the default. The compare is unsigned, so a negative score, which gives a negative index, also goes to the default. That is one instruction doing the work of the default label and the cases below 6.

The last six lines are the two returns. adrp x9, 0x100000000 and add x9, x9, #0x7d0 form the address 0x1000007d0, the start of __TEXT,__const from section 3.2. ldr w0, [x9, w8, UXTW #0x2] loads the 32-bit word at that address plus four times the index. The 20 bytes at file offset 2000 are 1, 2, 3, 4, 4 as little-endian words, so the load returns the grade. The default path is mov w0, #0x0 and ret.

Basic block: a run of instructions with one entry at the top and one exit at the bottom. Control enters only at the first instruction and leaves only after the last. The dossier's basic_blocks lists three for _grade: 0x100000518 to 0x10000053c with successors 0x10000053c and 0x10000054c, and the two leaf blocks with no successors. Lesson 33 builds the decoder and the block splitter that produce the same partition from bytes.

The same function on x86-64

Fourteen instructions, the same shape. The multiply is one instruction, IMUL RAX, RAX, 0x66666667, and the two shifts are 34 and 63 again. XOR EAX, EAX sets the default return value to zero before the compare, so the default path needs no extra block and the function has one RET. The table is at 0x1000b4, which is .rodata plus 0x14. The listing shows that address as a plain number because Ghidra applied the relocation when it loaded the object. Section 4.6 returns to the XOR line, because the decompiler wrote it in a way that hides the zero.

Where the no-return warnings go

raw_result.limitations is empty for _grade. When a function calls something Ghidra marked as never returning, the scan can stop there, and this list names the call site. On macOS and Linux, rea runs a repair script after the import. It clears wrong no-return flags on six common library names, so the bodies you read here are the repaired ones. The docs state the effect of a flag that stays: "An inferred no-return call can terminate that body before subsequent bytes." ghidra §Admitted function-analysis semantics

What to do with this
  • Read assembly in groups: constants, arithmetic, the compare and branch, the returns.
  • Treat an unsigned compare after a subtract as a bounds check that also rejects negatives.
  • Name the table an adrp and add pair points to, then read its bytes at the file offset.
  • Check raw_result.limitations for a terminal call before you trust the body size.

The id is a hash of the semantic content

Semantic projection: the view of the record that the id hashes. It keeps subject.digest, subject.format, and subject.architecture, and it drops subject.name and subject.local_path. The id is ev_ followed by the SHA-256 of that projection in canonical JSON. Object keys are sorted as RFC 8785 requires. parseEvidence recomputes the hash on every record it reads and rejects a mismatch with "Evidence semantic identifier does not match its record".

You can do the same check with a few lines of Node. The script below sorts keys, serializes without spaces, drops the two display fields, drops a null coverage field, and hashes.

import { createHash } from "node:crypto";
import { readFileSync } from "node:fs";

const canonical = (value) => {
  if (value === null || typeof value !== "object") return JSON.stringify(value);
  if (Array.isArray(value)) return `[${value.map(canonical).join(",")}]`;
  return `{${Object.keys(value).sort().map((key) => `${JSON.stringify(key)}:${canonical(value[key])}`).join(",")}}`;
};

const file = JSON.parse(readFileSync(process.argv[2], "utf8"));

const { evidence_id, subject, relationship_coverage, ...rest } = record;
if (relationship_coverage !== null && relationship_coverage !== undefined) rest.relationship_coverage = relationship_coverage;
const projection = {
  subject: subject === null ? null : { digest: subject.digest, format: subject.format, architecture: subject.architecture },
  ...rest,
};
const digest = createHash("sha256").update(canonical(projection)).digest("hex");

ResidualUnknown, record_unknown, and coverage

An unknown is a durable record with its own id and revision chain, and an empty list in any result tells you to check coverage.

The _percent_change dossier in capture/out/10-mcp-09-analyze-function-percent-change-O1.json lists "callees": []. An agent reads that line and writes that the function calls nothing. What an empty list proves

The dossier has an empty callees array and, 840 lines later, a limitation about it. Callees hold resolved targets only. The record says that this set is complete: relationship_coverage.status is complete, and unresolved_calls is empty. Complete means that Ghidra returned every resolved call reference. It does not mean that Ghidra found every call the program can make at run time.

The provider documentation states the same limit in one sentence: "Callers/callees contain only resolved functions." ghidra Admitted function-analysis semantics

The design rule behind every rea tool is shorter still: "Missing coverage is unknown, not absence." design Define the contract

Relationship coverage: the field relationship_coverage of an Evidence record, which states how complete the caller and callee sets are. Its status is complete, partial, or unknown. A partial value lists its limitations and can name the limited direction. An unknown value gives a reason. When a provider reports no coverage for procedure_callers or procedure_callees, rea writes unknown. A record of any other operation that reports no coverage has null.

Provider caveats stay in limitations and do not make the coverage partial. The same contract sets the limit of complete: "complete means that set was returned without a known read limit; it does not claim every possible runtime edge." design Define the contract

One part of the dossier does declare its coverage in numbers. The value flow reports whether it was truncated and how many operations, inputs, and edges it omitted. inspect-evidence-bundle repeats those numbers for every dossier in a bundle.

A zero here is a count that rea stands behind. An empty array elsewhere is a count with no such statement. The contract says what those fields are for: "native_dossier.value_flow independently reports truncation, unavailable or unknown metadata." mcp Tool results

AnalysisSnapshot and the exact-match answer cache

A snapshot caches exact answers under a query id bound to the target digest and the profile digest, and the dispatch of one mutating call turns the cache off.

The capture ran rea function fixtures/ledger-arm64-O1 NAME --provider ghidra four times, once per function, and each run took between 7 and 8 seconds (capture/out/00-commands.txt). Every run imported the same 33,872 bytes into a fresh Ghidra project and threw the project away. You want the second question about the same file to be free. When you finish this section, you can say which calls a snapshot can answer and build the query id by hand. You can also predict when rea refuses to replay or to save.

Three things called a snapshot

The word covers three things in rea, and only one of them is a cache you can keep.

Target snapshot: the private copy of the input that the Ghidra launcher imports with -readOnly and -deleteProject. It is deleted when the session closes, and nothing of the analysis survives it: "Each new provider session still imports the target into a fresh temporary project." mcp Ghidra first-query deadlines and recovery

Analysis snapshot cache: the in-memory table of one session, AnalysisSnapshotCache, which holds up to 10,000 entries for one target identity. This is the cache this section is about.

Snapshot file: the JSON file that close_binary writes and open_binary reads. It holds the target identity, the provider binding, the cache entries, and the session's Evidence bundle. The CLI documentation says what it is and what it is not: "These are cached observations, not a saved provider database: only eligible exact queries can reuse a result, and new or live queries can still require provider startup." cli Save and reuse analysis snapshots

The query id

Query id: query_ followed by the SHA-256 of canonical JSON holding four things: the target, the binding, the operation, and the parameters. The target is the path-free identity, sha256, kind, format, and architecture. A raw-binary target also carries its entry_point. The binding is the provider and its analysis profile. For the capture that is the digest that starts 01b5d08b, executable, mach-o, arm64, Ghidra 12.1.4, and the profile below.

The parameters are version strings, one per observation contract that the Ghidra adapter makes. The digest is the SHA-256 of the canonical JSON of provider and parameters. A cache entry matches only when the binding's provider and digest equal the selected profile's. A release that moves function_references from -v2 to -v3 changes the digest. Every entry made under the old digest then stops matching. That is what exact means in the thesis of this section.

Version 6.5.0 is such a release. It added four contracts and moved function_boundary_observations from ghidra-terminal-call-limitations-v1 to ghidra-function-boundary-limitations-v3. No 6.4.0 snapshot entry matches a 6.5.0 session. One Ghidra session made all eight rows of the bundle summary, so all of them carry the digest 966e6016… (export and import).

Which calls the cache answers

isSnapshotCacheable decides, before any provider runs, whether a call can be answered from the cache. A call qualifies when all of these hold.

  • The operation is not one of the stateful ones, health, current_address, current_procedure, current_document, goto_address, or list_documents.
  • An operation that is scoped to a document names its document.
  • An operation that defaults to the cursor, such as xrefs, names its address.
  • The capability declares mutatesArtifact: false, a cachePolicy other than live, and no permission change.
  • Its cachePolicy is snapshot, or it does not write to the file system.

The Ghidra adapter marks every operation except the mutating ones and list_documents with cachePolicy: "snapshot". prepareSessionExecution computes the id and looks it up. BinarySession returns a hit without touching the provider. The replayed answer carries one extra limitation: "Loaded from a local REA analysis snapshot; this call did not re-run the provider.".

The replayed record names the path of the target that is open now. The function rebindEvidenceToTargetPath writes that path into the stored record. The evidence_id does not change, because the path is outside the hash. On Windows, Ghidra must admit the source file before a replay, so a cache hit can still start the provider.

On a miss the provider runs, and the result is bound to the profile and the target. An Evidence record is then created and recorded, and a cache entry is stored under the id.

The capture shows no replay, because no two of its 25 MCP calls had the same operation and parameters. The first Ghidra-backed call after open_binary was list_procedures, and it took between 6 and 7 seconds while the headless import ran. Every later call on that target took under 100 ms (capture/out/10-mcp-session.txt). Those later calls were fast because the bridge was already running, not because of the cache. A repeat of analyze_function with "procedure": "_percent_change" would have been the first replay.

Save and load

close_binary takes snapshot_path and overwrite. closeWithSnapshot drains the calls in progress, exports the snapshot, writes the file, and closes the provider. Its receipt adds primitive_entries, workflow_entries, and evidence_records. open_binary takes snapshot_path too, reads the file before it opens the target, and imports the entries into the new session. The capture closed both targets without a path, so its two close_binary results are null (10-mcp-15-close-binary-O1.json, 10-mcp-25-close-binary-O2.json). On the CLI the flag is --snapshot: "An exact CLI cache hit is normally read before starting a provider process." cli Save and reuse analysis snapshots On Windows the Ghidra provider can start first, because it must admit the source file.

Loading a file is a full check. The entries must be in canonical id order, and every query id is recomputed and must match. No id appears twice. Every entry must have an Evidence record in the bundle with the same profile and the same result. A bundle record for another target fails the whole file.

Writing is atomic: the file is staged with mode 0600, synced, and renamed or hard-linked into place. Importing into a session whose target or profile differs fails with "Analysis snapshot profile_mismatch: target, provider, or analysis profile does not match the active binary".

Invalidation before a mutating call

Some Ghidra operations write to the session database, such as annotate_native_function, which renames a function or adds a comment. Each of them lists mutates_artifact in its effects, and each carries a limitation that names the consequence.

Before rea sends such a call to the provider, BinarySession calls invalidateSnapshot. The cache is emptied and a flag is set. From then on every lookup returns nothing, every new result is not stored, and an export fails with "Analysis snapshots are unavailable because analysis metadata may have changed". The error adds the way out: export the Evidence with export_evidence_bundle, close the target without a snapshot, and reopen it. An import after a mutation is refused the same way.

At 6.5.0 the order is: invalidate, then call the provider. A failed reply cannot prove that the write did not reach Ghidra. So a mutating call that fails also turns the cache off. The 6.4.0 release used the other order and invalidated only after a successful call. The CLI documentation states the rule: "Dispatching a metadata write invalidates the active session's snapshot cache, even if its reply fails: the provider may already have applied the write." cli Save and reuse analysis snapshots

What to do with this
  • Repeat a query with the same parameters to get the cached answer, and read the added limitation.
  • Save a snapshot with close_binary and snapshot_path before you annotate anything.
  • Expect a profile_mismatch refusal after a rea upgrade, and run the analysis again.
  • Treat a snapshot as answers to past questions, never as a saved Ghidra project.

The assembly limit

Every assembly dimension carries two limitations, whether its status is unchanged or changed.

rea attaches these strings before any diff runs. The dossier's assembly is Ghidra's listing text, with the addresses and the resolved operands inside the text. The tool compares that text line by line. It does not decode the instructions, it does not know which operand bytes a linker will patch, and it cannot mask them. Two copies of the same code at different addresses diff as changed, and a relocatable object compared with its linked image diffs as changed. The same holds across engines: when the two dossiers come from different providers, both text dimensions become unknown with "Exact text comparison requires one provider identity.".

An unchanged assembly dimension therefore means equal text from one engine, and a changed one means different text. Neither is a statement about bytes. The byte-level proof zeroes the relocation fields and compares the referenced table as well. Lesson 36 builds that proof, and Part 7 runs it against the same fixture. The references dimension has a limit of its own, because it compares the endpoints and not the kinds: "Reference endpoints differ independently of provider reference-kind metadata.".

What the 2026 measurements add

The hazards in the grid are not special to this fixture. Liu, Raff, and Micinski measured eight decompilation systems in nine configurations in 2026 (arXiv 2609.05370). Candidates that passed every test of the benchmark still diverged on fuzzed inputs. That happened for 4.9 percent of them overall and for up to 13 percent in one system. The test set was 300 library functions and 287 functions with disclosed vulnerabilities. There the strongest refinement model raised Ghidra's build rate from 75 to 90 percent, and the behavioural match rate fell from 74 to 62 percent.

They traced the cause to invented fields, types, callees, and guards that replaced the visible unknowns a decompiler leaves behind. percent_change_wide.c is an invented type, and grade_thresholds.c is an invented guard. Both compile, both pass the ten naive cases, and both count as re-executable under a benchmark that recompiles and runs the assertions it includes. The authors propose per-function driver synthesis and fuzzing from the reference, which is leg one with a generated grid.

The lesson adds a third source for the constant check. The rea evidence pages describe a reconstruction project that compared instruction bytes while trusting the relocation target. A source literal of 0.0 passed against a target literal of 128.0 until the project audited 1,548 floating-point references. grade_case10_wrong.c is this manual's version of that defect, and read_table() is the audit.

What to do with this
  • Write the rebuild from the listing widths, then run it over a grid that wraps every intermediate.
  • Compile the candidate with the original flags and compare bytes only after you mask the relocation fields.
  • Read the bytes each relocation points at, because a wrong constant passes a masked compare.
  • Record the host and the compiler with every proof, because the trap cell and the bytes depend on both.

rea mcp: initialize, tools/list, and the startup deadline

rea mcp serves 207 tools over stdio after one initialize handshake, and the first Ghidra-backed call pays for the import under a server deadline the client does not share.

You added rea to the MCP configuration of your agent and asked it for the dossier of _grade. The client reported a timeout after one minute while a Java process kept running. Nothing was wrong with rea or with Ghidra. Two deadlines with two owners had crossed.

The capture kit drove rea mcp with a small client of its own and recorded 25 exchanges. This section reads the first ones and the log beside them. When you finish this section, you can read the initialize reply and the tools/list answer and register the server with one exact version. You can also set the client deadline that the first Ghidra call needs.

Starting the server

The published way to register the server is one mcpServers entry that runs the package through npx with the mcp command:

The docs ask for one exact version in a persistent registration install MCP Registry. A client that supports registry discovery finds the same stdio server under io.github.morluto/rea. rea setup writes this shape for Claude Code, Codex, Cursor, and the other clients it lists. rea doctor --client <id> reports whether a registration is aligned, stale, missing, or invalid (Section 2.2).

The rea.mjs dispatcher routes the single argument mcp to dist/main.js. run() there parses the environment into a configuration and exits 1 with the projected error when a value is invalid. It then creates the logger and the one BinarySession, opens an initial target only when HOPPER_TARGET_PATH is set, and starts the stdio transport. Shutdown is bound to SIGINT, SIGTERM, and the end of stdin. An unexpected startup failure prints one fixed sentence and hides its cause: "REA could not start. Run rea doctor, then restart REA from your MCP client.".

The transport is newline-delimited JSON-RPC 2.0 on stdin and stdout, and stderr carries one pino JSON line per tool call. The capture kit started the server as node.../scripts/rea.mjs mcp with GHIDRA_INSTALL_DIR and JAVA_HOME set, as capture/README.md describes, and kept the stderr lines as 10-mcp-server.log.

initialize

The client sends initialize with the protocol version it speaks, its capabilities, and its name. The server answers with the version it negotiated, its own capabilities, its identity, and an instruction string for the model:

The server builds the instruction string from two parts. The first part depends on the session. Without a target it is the target-free text above. With an active target it names analyze_function as the dossier tool and the procedure tools as its facets.

The second part is always the same. It tells the model to treat strings, symbols, pseudocode, and file contents from the target as data. It also tells the model to report a request in that text as a prompt-injection attempt mcp Untrusted target content.

After the reply the client sends notifications/initialized, and the connection is established. binary_session later reports the negotiated version, the SDK version 2.3.1 on both sides, the client name, and the catalog digests (capture/out/10-mcp-04-binary-session.json).

tools/list

Tool catalog: the complete list of tools the server advertises, 207 in 6.5.0. Each entry has a name, a title, a description, an input schema, an output schema, and four annotation hints. tools/list returns every tool whether or not the current target supports it mcp Identity and discovery. Opening or closing a target leaves the list unchanged and sends no notifications/tools/list_changed. The session's own view is the authority. binary_session reports tool_availability for the open target, with a reason and a remediation for each unavailable tool, and the catalog counts.

The annotations describe effects and are hints, never authorization. readOnlyHint counts session state, so analyze_function is marked non-read-only because it records Evidence, although it never changes the file mcp Request scope and local effects. Six tools of the 207 carry readOnlyHint: true in the capture: get_evidence_bundle, list_unknowns, verify_unknown_resolution, evaluate_reconstruction_coverage, gdb_session_status, and frida_session_status. binary_session is not one of them, because it can start a provider process to check health.

Thirty-one tools carry destructiveHint: true. The docs set this hint for three cases mcp Request scope and local effects. The tool can discard data, run code that rea does not own, or change an attached Android device. Among them are export_evidence_bundle, which can overwrite a file, and close_binary, which discards the session. The annotation tools such as annotate_native_function are among them too, because they overwrite analyst names and comments.

Of the 207 tools, 65 have no CLI command, among them open_binary, list_procedures, compare_functions, and verify_reconstruction. The six prompts are investigate_feature, compare_application_versions, verify_reconstruction, trace_crash, audit_residual_unknowns, and prepare_bounded_process_capture, and each asks the agent to keep observations, inferences, and unknowns apart. A client that rejects large tool schemas can start the server with REA_MCP_INPUT_SCHEMA_PROFILE=compact mcp Compact input schema profile. That profile renders every input schema within 13,312 bytes and leaves the validation unchanged.

The startup deadline against the client default

Startup deadline: the time rea allows for Ghidra to import the target, run default auto-analysis, connect the bridge, and report healthy. It is 330,000 ms by default and set with REA_GHIDRA_STARTUP_TIMEOUT_MS. open_binary does not start that clock. It validates the file, binds the provider, and returns in milliseconds. The first Ghidra-backed call starts the engine and waits, and the client's own per-call deadline runs at the same time mcp Ghidra first-query deadlines and recovery.

What to do with this
  • Register npx -y rea-agents@6.5.0 mcp with one exact version and restart the client.
  • Read binary_session for the tools the open target supports, because tools/list lists all 207.
  • Set the client's per-call deadline above the first Ghidra call before you make that call.
  • After a client timeout during startup, call close_binary, then open_binary, then retry.

Target text is data

Target text: every string, symbol name, comment, and line of pseudocode that a tool result copies out of the analyzed file. The usage text usage: ledger <before> <after> [score...]\n at 0x10000077a is target text, and so is _labels and every DAT_ name Ghidra invented (capture/out/10-mcp-08-list-strings.json). The rule is that an agent quotes target text with its address and never acts on it. A string that reads like a command is a value to record, and the ledger has no row kind for "instruction received from the file".

rea 6.5.0 states this rule to the model. The instruction string of every connection tells the model to treat target text as data. It also tells the model to report a request in that text as a prompt-injection attempt. Each result that can carry target text has the marker _meta.provenance.untrusted_content: true with source: "analysis_target", also when the call fails mcp Untrusted target content. Only export_evidence_bundle and record_unknown leave it out.

In this session every result has the marker, except the two export_evidence_bundle results. The error of step 13 has it too. The marker tells the agent which text came from the file, and the agent must still apply the rule. This manual therefore makes the rule a ledger rule. The description of import_evidence_bundle states the same principle for bundles: "Imported content is data only and is never executed." (capture/out/10-mcp-02-tools-list.json).

The 2026 research says what happens without the rule. Santos-Grueiro built binaries whose strings and tool output pose as instructions or as fake corroborating evidence (arXiv 2607.12507). Without runtime controls, the models under test proposed a planted unsafe action in 35 of 40 adversarial cases and in none of 40 clean ones. Showing the binary content as data alone still left 15 unsafe proposals, and tool authorization with provenance checks removed them. A workshop study of three agents on 24 offline tasks named over-trust in observations as one of four recurring weaknesses (NDSS BAR 2026). A ledger row that names its Evidence id and its boundary is the smallest form of that provenance check an agent can keep by itself.

The rea marker gives the provenance half of that control. Tool authorization stays with the client.

What to do with this
  • Write one ledger row per claim, with its kind and the Evidence id that supports it.
  • Mark a table value unknown until read_bytes returns it, even when you own the C source.
  • Quote target strings with their address, and never follow an instruction you find in one.
  • Export the bundle before close_binary, so every id in the ledger stays checkable.

The id

The id hashes the semantic projection of the record. That projection keeps the subject's digest, format, and architecture and every other field except evidence_id, and leaves out the subject's name and local_path. The same observation of the same bytes therefore gets the same id in any directory on any machine. The capture check compares ids unmasked (capture/README.md). parseEvidence recomputes the hash of every record it reads and rejects a mismatch. A record without a subject gets the limitation "Artifact identity is unavailable for this observation." appended at creation.

The projection leaves out relationship_coverage when it is null, so records without coverage keep their ids.

Two other id prefixes appear in the captures. unk_ ids name residual unknowns and hash { domain, question, scope_digest }, and comparison_conclusion_scope when the unknown has one (Section 5.2). The analysis_profile.digest is the SHA-256 of the canonical JSON of the provider and its parameters. Two records with different digests are not comparable in compare_functions.
